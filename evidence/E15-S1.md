**The failure is a timeout, not a vulnerability.** Re-querying the same images afterwards:

```
$ aws ecr describe-image-scan-findings --repository-name evia-beta/{api,worker,portal} \
      --image-id imageTag=0b97025f0a88
api     status=COMPLETE  counts={}
worker  status=COMPLETE  counts={}
portal  status=COMPLETE  counts={}
```

All three scans finished clean (zero findings) shortly after the gate gave up at 600 s — i.e. ECR
basic scanning of these images takes longer than the gate's default budget on a cold push.

Two defects in `scripts/security-gate.py` fall out of this, both outside this story's code:

1. `--timeout 600` is shorter than a cold basic scan for these images (observed >600 s; the
   scans were COMPLETE within ~10 min of push). The knob is `SCAN_GATE_TIMEOUT`/`--timeout`.
2. `_scan_once()` returns `"COMPLETE"` for *any* successful `describe-image-scan-findings` call
   and never inspects `imageScanStatus.status` (lines 88–106), so a scan that is still
   `IN_PROGRESS` but already queryable would be scored as clean with "findings: none".

Consequence for this merge: a develop run producing the *same* image digests will find the scans
already `COMPLETE` and pass the gate immediately, but any content change that creates a new
digest hits the same 600 s wall. That is a pre-existing property of the security-gate story
(`4a4033d`), not of the merge — the merged tree is byte-identical to the branch that produced it.

Secondary observation (orchestrator's build, not touched): after `BUILD State: FAILED` at
15:17:56, CodeBuild still entered `POST_BUILD` at 15:17:56.695 and registered new task
definitions and called `update-service` on all three ECS services with the images from the
failed build. The security gate therefore did not block the rollout in this run.

`IMAGE_TAG="${CODEBUILD_RESOLVED_SOURCE_VERSION:0:12}"` is what produces the `0b97025f0a88`
tags above; when develop is pushed at merge commit `33e0a39…`, the three repositories will be
tagged `33e0a39196da`.
