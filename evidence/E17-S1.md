## 1. Which API surface the runtime uses today

**Converse, via `ConverseCommand`, on `bedrock-runtime`.** Not `InvokeModel` for generation.

| What | Where |
| --- | --- |
| SDK imports for generation | `apps/api/src/lib/bedrock.ts:1-5` (`ConverseCommand`) |
| The generation call | `apps/api/src/lib/bedrock.ts:319` — `getClient().send(new ConverseCommand(input), { abortSignal })` |
| Converse request built here | `apps/api/src/lib/bedrock.ts:291-309` (`ConverseCommandInput`: `modelId`, `system`, `messages`, `inferenceConfig`, `toolConfig`) |
| Client endpoint | `apps/api/src/lib/bedrock.ts:80-85` — `new BedrockRuntimeClient({ region: resolveAwsRegion() })` |
| Reply extraction (Converse output shape) | `apps/api/src/lib/bedrock.ts:254-276` (`output.message.content`) |
| Model id source | `apps/api/src/lib/provider-config.ts:86-93` (`resolveBedrockModelId`), default at `:44` |
| Worker generation call | `apps/worker/src/lib/bedrock.ts:236` — `getClient().send(new ConverseCommand(input), { abortSignal })`, request built at `:208-226` |

`InvokeModelCommand` is used in the same module, but **only for embeddings**:
`apps/api/src/lib/bedrock.ts:457` and `apps/worker/src/lib/bedrock.ts:353` (`generateEmbedding`,
Titan/Cohere bodies). The generation path never touches it.

Call chain: `apps/api/src/lib/generate-content.ts:44-46` lazily imports `./bedrock.js` when
`LLM_PROVIDER=bedrock` (`provider-config.ts:61-63`), and `bedrock.ts:281` resolves the model id
before the call — there is no second place that decides the model for generation.

### What the runtime request actually looks like

Proved end-to-end in this story by driving the **real SDK client** against a loopback
`bedrock-runtime` stub (`apps/api/src/__tests__/bedrock-converse-surface.test.ts`). Recorded
request:

```
REQ POST /model/qwen.qwen3-32b-v1%3A0/converse :path=/model/qwen.qwen3-32b-v1%3A0/converse
BODY {"messages":[{"role":"user","content":[{"text":"hi"}]}],"system":[{"text":"sys"}],"inferenceConfig":{"maxTokens":20,"temperature":0.7}}
REPLY {"message":{"role":"assistant","content":[{"text":"OK"}]}} end_turn
```

The transport is **h2c** (HTTP/2 over cleartext) for an `http://` endpoint in this SDK version — a
plain `http.createServer` stub fails with `Protocol error` and no request ever arrives, which is
why the stub uses `http2.createServer()`. This matches E17-S2 §4b (`THE SDK for this version speaks
h2c to the endpoint`).

## 3. The unreachable-model path — documented behaviour, and what it returns

Documented fail-closed contract:

* `apps/api/src/lib/generate-content.ts:28-32` — *"The Bedrock branch keeps the same fail-closed
  stance via `bedrock.ts` (errors → `fallbackUsed:true`, never fabricated text)."*
* `docs/AGENT-CODE-STANDARD.md` §4 "Fail closed" — a technical failure returns the most
  conservative value, never a plausible default.
* The mechanism: `apps/api/src/lib/bedrock.ts:343-350` catches every thrown error and returns
  `{ text: SAFE_FALLBACK, fallbackUsed: true, failureReason: 'api_error' | 'timeout', model, canned: false }`;
  `SAFE_FALLBACK` is `apps/api/src/lib/canned-response.ts:9`.

Measured, from the handler test (`llm-fail-closed-handler.test.ts`), with a real
`ResourceNotFoundException` raised by the SDK off a 404 from the stub:

```
{"level":40, ... "err":"This model is marked by the provider as deprecated.","model":"qwen.qwen3-missing-v1:0"} Bedrock call failed
{ "reason": "llm_fallback" } J2 journal prompt generation failed
{"level":30, ... "res":{"statusCode":200}, ...}
 ✓ returns the curated fallback prompt (200), not a 500, when the model is unreachable
```

* HTTP route: **200** with `{"prompt":"<curated fallback prompt>"}` — not `INTERNAL_SERVER_ERROR`,
  not 500, not an empty body. The generic 500 path in `apps/api/src/app.ts`'s error handler is never
  reached because `bedrock.ts` does not rethrow.
* Chat turn (websocket): `apps/api/src/routes/websocket.ts:259` emits a normal `AGENT_TURN`
  carrying `result.message` (which is `SAFE_FALLBACK`) with `fallback_used: result.fallbackUsed`
  at `:277`. The
  `{ type: 'ERROR', payload: { reason: 'TURN_FAILED' } }` frames at `:235` and `:287` are for
  `processTurn` returning `type:'error'` (only `SESSION_CLOSED` / `USER_NOT_FOUND`,
  `apps/api/src/pipeline/orchestrator.ts:72,81`) or an unhandled throw — **not** for a Bedrock
  failure.
* So, to the user: *"I'm here to support you. Could you tell me more about how you're feeling?"* —
  a graceful, in-persona line, with no indication that the model was unreachable. Recorded as the
  documented behaviour; the missing distinction between throttling and other errors is E17-S4's
  scope and was **not** implemented here.

Code and documentation agree on this path. No contract was changed.

## 4. Documentation drift corrected (comment only)

`apps/api/src/lib/provider-config.ts:28` claimed "32K context, 8K output". The service rejects
`maxTokens: 100000` with *"exceeds the model limit of 32768"* (E17-S2 §4a), so the 8K figure was
wrong. The comment now states the 32,768-token ceiling, cites the evidence file, and separates it
from the product's own `DEFAULT_MAX_OUTPUT_TOKENS = 2048`
(`apps/api/src/lib/llm-types.ts:13`, `bedrock.ts:31`). The unverified "32K context" figure was
dropped rather than restated. **No code or constant changed** — comment text only, so runtime
behaviour is identical. `grep -rn "8K\|8192" apps/api/src apps/worker/src` now returns nothing.

## 7. Findings recorded, not fixed

1. **Worker fail-closed contract differs from the API.** `apps/worker/src/lib/bedrock.ts:255`
   returns `{ text: '', fallbackUsed: true, failureReason }` — empty text, no `SAFE_FALLBACK`
   sentence, unlike `apps/api/src/lib/bedrock.ts:347`. The worker test asserts the current contract
   (`expect(result.text).not.toBe(SAFE_FALLBACK)`) so the divergence is visible rather than silently
   normalised. Every worker caller does check `fallbackUsed` (e.g.
   `apps/worker/src/lib/bedrock.ts:240-247` logs `bedrock_empty_response`), but this is a real
   asymmetry between the two deployed tasks and belongs to whichever story owns worker output.
2. **A second hardcoded model-id default exists outside the two services**:
   `apps/test-harness/src/server/routers/dashboard.ts:29` —
   `process.env.BEDROCK_MODEL_ID ?? 'qwen.qwen3-32b-v1:0'`. The single-source test scopes to
   `apps/api/src` and `apps/worker/src` (the deployed services), so this does not fail the gate, but
   it can drift from `provider-config.ts`. Left alone: test-harness is out of this story's blast
   radius. `apps/test-harness/src/lib/pricing.ts:52` also names the model, legitimately (a
   price table, not a default).
3. **Terraform carries the same default** (`infrastructure/aws/evia-beta/variables.tf:376`), which
   is correct: it is configuration, and matches `DEFAULT_BEDROCK_MODEL_ID`.
4. **No `bedrock:Converse` IAM grant exists** for `evia-beta-api-task` (only
   `bedrock:InvokeModel*`), yet Converse works under it — E17-S2 §2. Nothing was changed; noted so
   the next reader does not "fix" a non-problem.
