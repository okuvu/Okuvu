## Clause 1 — a green build deploys to ECS automatically

Proven by the webhook path rather than by assertion. Pushes to `develop` start a
build with no human step:

```
$ aws codebuild list-builds-for-project --project-name evia-beta-build   # initiator on every build
GitHub-Hookshot/51d2642
```

Build `f0f5b101` (push `d56b5c4`) moved api 31->32, worker 31->32, portal 29->30
with rollout COMPLETED on all three, and `GET https://api.okuvu.in/health`
returned `commit: d56b5c491b8b`, which equals the ECR image tag on all three
repositories. Code identity between the pushed commit, the built image and the
serving container is therefore closed, not inferred.

## Clause 2 — a tested rollback

Proven twice, once by an unplanned production event and once deliberately.

**Unplanned, 29 Oct.** Build `02860232` registered api:22, worker:22, portal:20
and updated all three services. api:22 crash-looped with `ERR_MODULE_NOT_FOUND`
(a new library import missing its `.js` extension under node ESM — typecheck and
Vitest both resolve extensionless specifiers, so nothing caught it before the
container). The circuit breaker fired at 06:34:06Z with "tasks failed to start"
and ECS rolled the api back to api:21, which kept serving throughout. A live
rollback under real failure is stronger evidence than a staged test.

**Deliberate.** The same mechanism was executed once under control while
diagnosing, and reverted.

**Breaker configuration, read back from AWS at 2026-10-30T04:47Z:**

```
evia-beta-api     breaker_enable True  rollback True
evia-beta-worker  breaker_enable True  rollback True
evia-beta-portal  breaker_enable True  rollback True
```

## Clause 3 — the pipeline does not report success after a rollback

The rollback exposed a second defect: `aws ecs wait services-stable` returns
success *after* a circuit-breaker rollback, because a rolled-back service is
stable. Build `02860232` therefore reported SUCCEEDED while serving old code.

Fixed in `buildspec.yml`: the build now records every task-definition ARN it
registers and exits non-zero unless each service's PRIMARY deployment is that
ARN. Verified in build `16f3638b`, which passed the new check.

## Clause 4 — the runbook entry exists

`docs/ONCALL-RUNBOOK.md`, 921 lines. Section 2.3 derives the rollback target
from ECR (task definitions are immutable, so the target is "newest minus one"),
and section 2.4 is titled "Confirm the rollback — and why `wait services-stable`
is not proof", which is the exact trap this story tripped over. The runbook is
merged on `develop`.

The clinical sign-off on that runbook's escalation section belongs to E20-S2 and
is not claimed here.

## What this does not prove

- Rollback of the *worker* or *portal* is configured but has only been exercised
  on api.
- One task per service, single AZ: a rollback is recovery, not zero-downtime.
- The runbook's rollback section has never been executed end to end by an on-call
  engineer who was not the author.
