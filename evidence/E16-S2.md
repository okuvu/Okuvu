## Acceptance criterion

> Apex and www route to the therapist portal.

## Commands and raw output

Routing rule on the 443 listener (no code change was involved — the rule predates the story):

```
$ aws elbv2 describe-rules --listener-arn <443 listener of evia-beta-alb> \
    --query 'Rules[].{p:Priority,h:Conditions[0].Values[0],a:Actions[0].TargetGroupArn}'
[
    { "p": "10", "h": "www.okuvu.in",
      "a": ".../targetgroup/evia-beta-portal-tg/713547dbcab9b3b7" },
    { "p": "default", "h": null,
      "a": ".../targetgroup/evia-beta-api-tg/7de5e7f973e79f4a" }
]
```

The priority-10 host condition carries `okuvu.in`, `www.okuvu.in` and
`portal.okuvu.in`; all three forward to `evia-beta-portal-tg`. The default action
still sends unrecognised hosts to the api target group.

HTTP behaviour over TLS (orchestrator, 2026-10-28T20:58Z):

```
$ curl -s -o /dev/null -w '%{http_code}' https://okuvu.in/          -> 307  (into /auth)
$ curl -s -o /dev/null -w '%{http_code}' https://www.okuvu.in/      -> 307  (into /auth)
$ curl -sI http://okuvu.in/ | head -1           -> HTTP/1.1 301 Moved Permanently
$ curl -s -o /dev/null -w '%{http_code}' https://okuvu.in/auth     -> 200
$ curl -s -o /dev/null -w '%{http_code}' https://okuvu.in/dashboard -> 307 (portal stays closed)
$ curl -s -o /dev/null -w '%{http_code}' https://okuvu.in/privacy  -> 200 (after E19-S2)
```

## Recorded precisely, not relabelled

The criterion names a 200/308 at the apex. What the apex actually returns is **307**
into `/auth`, then 200 on the login page. Same behaviour (the apex lands on the
therapist login), different status code. Accepted by the orchestrator as meeting the
intent; recorded here as observed rather than rounded to the criterion's wording.
