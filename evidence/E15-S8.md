| `aws_cloudwatch_event_target.task_stopped_ops_sns` | target `arn:aws:sns:ap-south-1:562654496378:evia-beta-ops-alerts`, `target_id = ops-alerts-sns`, full event as the message body |

No IAM role is needed: an SNS target in the same account is authorised entirely by the topic policy. That is
the answer to "whatever IAM or topic policy is needed" — a role here would be dead weight, and it would not
work anyway, because the failure is a resource-policy denial, not an identity one.

The rule is a free path: ECS Task State Change is an AWS service event on the **default** bus, and
EventBridge does not charge for those (the $1.00/million rate is for custom events on the default bus and
for any event on a custom bus). No new log group, no metric, no Lambda.

## 2. The event filter, derived from measurements rather than from documentation

The naive filter — `lastStatus = STOPPED` — pages on every deployment and every scale-in. The story's
phrase is *"stops while desired is RUNNING"*, which suggests filtering on `desiredStatus`. That filter alone
is wrong for the verification path this story is required to ship, and the measurement below is the whole
reason the final pattern has an `$or` in it.

### 2.1 Measured: what a failing task actually emits

A throwaway task definition (`evia-beta-e15s8-probe`, the image the api service was running,
`entryPoint /bin/sh -c`, `command exit 3`, no `logConfiguration`) was run with `run-task` — same subnets,
same security group — while a deliberately broad probe rule (`lastStatus STOPPED` only) fed a temporary SQS
queue:

```
$ aws ecs run-task --cluster evia-beta --task-definition evia-beta-e15s8-probe:1 \
    --launch-type FARGATE --network-configuration … --overrides '{"containerOverrides":[
    {"name":"probe","command":["exit 3"]}]}'
task arn:aws:ecs:ap-south-1:562654496378:task/evia-beta/b143ec4446ce434cade5d08e4ab1bbe9

### event delivered to the probe queue
{
 "source": "aws.ecs", "detail-type": "ECS Task State Change",
 "detail.lastStatus":    "STOPPED",
 "detail.desiredStatus": "STOPPED",          <-- not RUNNING
 "detail.stopCode":      "EssentialContainerExited",
 "detail.stoppedReason": "Essential container in task exited",
 "detail.group":         "family:evia-beta-e15s8-probe",
 "detail.containers[].exitCode": [3]
}
```

**A standalone task that fails reports `desiredStatus = STOPPED`.** ECS sets the desired status to STOPPED
because nothing wants the task to keep running; only a *service* keeps `desiredStatus = RUNNING` while its
task is being replaced. So a `desiredStatus = RUNNING`-only rule would be silent for exactly the task the
verification is required to start, and the acceptance sentence and the verification requirement could not
both be true.

Two further measurements, same session:

```
$ # a service task, seen live while another change was rolling the api service:
$ aws ecs describe-tasks --cluster evia-beta --tasks arn:…:task/evia-beta/a64ec5e0727d4edf8d3d2b536b26e093
{ "grp": "service:evia-beta-api", "startedBy": "ecs-svc/9356838091311839752",
  "td": "…task-definition/evia-beta-api:26",
  "stopCode": "EssentialContainerExited", "reason": "Essential container in task exited" }
   # matched the broad probe rule too: a real service death, not a synthetic one

$ aws ecs run-task … command 'sleep 300'  then  aws ecs stop-task …
{ "detail.lastStatus": "STOPPED", "detail.desiredStatus": "STOPPED",
  "detail.stopCode": "UserInitiated", "detail.containers[].exitCode": [137] }
```

That last row is the trap: an intentional stop exits **137** (SIGKILL after `stopTimeout`). A rule that
matched "exit code != 0" without also checking `stopCode` pages on every `stop-task` and on any deployment
where the app does not trap SIGTERM — precisely the noise the E15-S6 alarms were tuned to avoid
(worker deploys at `minimumHealthyPercent = 0`).

### 2.2 The pattern that survived

```json
{
  "source": ["aws.ecs"],
  "detail-type": ["ECS Task State Change"],
  "detail": {
    "clusterArn": ["arn:aws:ecs:ap-south-1:562654496378:cluster/evia-beta"],
    "lastStatus": ["STOPPED"],
    "$or": [
      { "desiredStatus": ["RUNNING"] },
      { "stopCode": ["EssentialContainerExited"],
        "containers": { "exitCode": [{ "anything-but": [0] }] } }
    ]
  }
}
```

- branch 1 — the service still wanted the task running when it vanished: crash, spot reclaim, task definition
  deleted mid-flight. This is the literal "stops while desired is RUNNING" case.
- branch 2 — a one-off task whose container failed on its own: `stopCode EssentialContainerExited` **and** a
  non-zero exit code. `UserInitiated` and `ServiceSchedulerInitiated` stops (deployment, scale-in,
  `stop-task`) are excluded, and so is a clean exit 0, which is how a successful batch job ends.
- both branches and the `$or` inside `detail` were verified by delivery, not by reading the pattern syntax:
  the rule fired on the failing task and stayed silent on the deliberate stop.

### 2.3 Measured behaviour of the final pattern

Three runs, each with a clean queue, on the real cluster:

| test | task | result |
|---|---|---|
| interim pattern (`containers.exitCode anything-but 0`, no `stopCode` term), run-task exits 3 | `…daae40d4ba4b49abbdf3adbec51dd874` | **1 message** — matched, as intended |
| same interim pattern, task stopped with `stop-task` | `…b43488257ae4` | **1 message** (`UserInitiated`, exit 137) — the noise case, and the reason `stopCode` was added to branch 2 |
| final pattern, task stopped with `stop-task` | (throwaway task, `sleep 300`) | **0 messages** — correctly silent |
| final pattern, run-task exits 3 | `…c4333c87e4be40b687fe17bc6599ca2a` | **1 message** — matched |

During those runs, four unrelated `family:evia-beta-dbprobe` tasks on the same cluster completed with exit 0.
They produced **no** message under either pattern — the exit-code term in branch 2 excluded them even before
`stopCode` was added — which is the practical form of "don't page on a successful one-off job".

## 3. The three alarms, the cluster setting, and why they cannot be split

`observability.tf`: the `locals.desired_task_counts` block and the
`aws_cloudwatch_metric_alarm.service_running_tasks_low` `for_each` resource are **deleted**, and a comment
records why. `ecs.tf`: `containerInsights` is set to `"disabled"` rather than having the block removed —
an explicit value makes the provider issue `UpdateClusterSettings`, whereas a removed block is a no-op and
would leave the setting enabled while the plan claimed otherwise.

Ordering is enforced by construction: both edits are in one change set, so one apply does both. This is not
housekeeping — the alarm has `treat_missing_data = "breaching"`, so with the metric namespace off and the
alarm still present, there is no data to evaluate and it sits in **ALARM** permanently. Three alarms paging
about a metric that no longer exists is worse than no alarm: it trains the on-call to ignore the topic.

Two honest qualifications:

1. **$32.40 is an upper bound on the metric line, and a tight one.** 108 is the live stream count from
   `list-metrics`; if a service is removed the count drops. It is not padded — every one of the 108 is a
   distinct dimension combination that CloudWatch bills separately.
2. **The alarm $0.30 is exact** (3 alarms × the published rate) and stops the moment the alarms are
   destroyed.

Not counted, deliberately: the `/aws/ecs/containerinsights/evia-beta/performance` log group stops receiving
once Insights is off (3.6 MB stored, 1-day retention) — that is a few cents of Logs ingestion, not a
computable figure without the per-day ingestion numbers, so it is left out rather than guessed. The log
group itself is **not** deleted here (deleting a log group holding the last 24 h of Container Insights
performance data is a separate decision, and it costs nothing while empty).

## 6. What the orchestrator must do

**6.1 — pass `image_tag`, or the apply rolls production back.** `terraform.tfvars` (gitignored) still pins
`image_tag = "ce85c8389023"` while all three services run `6de0209c9dd9` (`evia-beta-api:26`,
`evia-beta-worker:26`, `evia-beta-portal:24`). Applying with the tfvars as-is re-points every service at an
older image. This is the pre-existing E15-S6 drift, still unfixed, and it is still the one thing in this
stack that can break production on apply. Use `-var image_tag=6de0209c9dd9` (what the plan above used).

**6.2 — apply, once.** 3 add, 1 change, 3 destroy. The three destroys and the cluster change must land in
the same apply (§3). The apply takes seconds; nothing restarts.

**6.3 — run the verification script.** After the apply:

```
./scripts/verify-e15s8-task-stop-alert.sh
```

It is committed with this change and it is the acceptance evidence, not a nicety: preflight (rule enabled,
target is the topic, topic policy admits the rule, `containerInsights = disabled`, zero
`*-running-tasks-low` alarms left, sink queue present) → registers `evia-beta-verify-task-stop` from the
image the api service is running (`/bin/sh -c 'exit 3'`, no log configuration, no Okuvu code path) →
`run-task` in the api service's own subnets and security group → waits for the message whose
`detail.taskArn` is that task → prints the SNS envelope, task ARN, `stopCode`, `stoppedReason` and exit code
→ deregisters the throwaway definition via `trap`. It never stops, scales or deregisters a service, and it
deletes only its own message from the sink. Cost: about $0.001 of Fargate.

Expected output ends:

```
  alert received (SNS envelope: True)
  source / detail-type : aws.ecs / ECS Task State Change
  task ARN             : arn:aws:ecs:ap-south-1:562654496378:task/evia-beta/<id>

PASS — an ECS task that died on evia-beta published to evia-beta-ops-alerts
```

**47 s is measured**, not estimated: §7.2 is that exact script, run against an isolated
`-reh-` rule/topic/queue with identical resource shapes, with only the two post-apply state assertions
switched off (Container Insights was still enabled at the time).

**6.4 — after the apply, two things to expect.** `aws events list-rule-names-by-target --target-arn

`aws cloudwatch describe-alarms --alarm-name-prefix evia-beta`. If the script fails on the topic-policy
check, nothing was delivered and the rule is looking healthy — that is the fail-silent mode this policy
exists to prevent, and the script names it.

## 8. What this change gives up, stated plainly

Container Insights was also the only source of per-service **CPU and memory** metrics for this cluster.
Nothing in this story replaces that: after the apply, the stack keeps ALB health/5xx alarms, the two RDS
alarms, the new task-stop rule, VPC flow logs and application logs — but "the api task is pegged at 100 % CPU"
is no longer observable from CloudWatch without going back to the container's own logs.

The honest options, none taken silently here: (a) accept it for a three-service beta whose capacity is
pinned and whose failure mode is "task gone", which the new rule covers better than the old alarm did;
(b) publish three or four hand-picked CPU/memory metrics from the app itself at ~$1.20/mo; (c) re-enable
Insights at $32.40/mo. The story's acceptance is specifically that running-task alerting no longer depends on
Container Insights, so (a) is the state delivered, and (b) is the follow-up if anyone misses the CPU chart.

  remains the only place a notification actually lands. The verification script reads the sink for that
  reason; the mailbox needs a human to click the link.
- `/aws/rds/instance/evia-beta-postgres/postgresql` still has no retention (unbounded log growth).
