# E15-S7 — documentation commits complete a green build without rolling ECS

Acceptance criterion (verbatim): *"a commit touching only docs/, evidence/ or plan/ completes a build but
does NOT change any ECS task-definition revision; a commit touching app or infrastructure code DOES roll
the services."*

Scope honoured: worktree `/opt/data/okuvu/wt-E15S7`, branch `feat/E15-S7-docs-no-deploy`, cut from
`origin/develop` at `6f1ab7f`. **No deploy, no `terraform apply`, no ECS service created, stopped,
scaled, updated or deregistered, no AWS resource changed.** The only AWS call made in this story is a
read-only `terraform plan -target` against a copy of the orchestrator's state (§4.3) and
`aws sts get-caller-identity`. §9 lists what is left for the orchestrator, including the live two-push
proof, which is theirs and which I have **not** done — this story is implemented and proven
deterministically, not verified live.

---

## 1. The mechanism question, and the answer the build can actually reach

CodeBuild clones the repository fresh for every build (`DOWNLOAD_SOURCE`), so the job has no idea
"what changed" in a push. It has to derive it. Two things are available inside the build, and only
two:

1. **What is running now.** Each service's PRIMARY deployment points at a task definition whose
   container image carries the tag the deploying build used, and `buildspec.yml` sets
   `IMAGE_TAG = ${CODEBUILD_RESOLVED_SOURCE_VERSION:0:12}` — *the tag is the commit SHA*. So ECS
   itself names the commit production was built from, with no extra state to keep.
2. **What is about to run.** The checked-out tree at `HEAD`, and `git`, which can compare two trees.

That turns "does this commit need a rollout?" into a tree question:

```bash
git diff --no-renames --name-only <deployed-sha> HEAD
```

If every changed path is inside `docs/`, `evidence/` or `plan/`, the code the services would run is the
code they are running, so the rollout is skipped. Anything else — app code, infrastructure, the
buildspec, a script, the lockfile, or a path nobody anticipated — is a deploy. If the answer cannot be
derived at all, it is a deploy (see §7, which is the part that matters most).

**Why ECS and not ECR for "the previous commit".** ECR holds a tag for every build that pushed images,
including builds that failed before the rollout: E15-S1 recorded exactly that — a build whose ECR scan
gate failed pushed `evia-beta/{api,worker,portal}:0b97025f0a88` and never legitimately deployed them.
The newest ECR tag is therefore a claim about what was *built*; the PRIMARY deployment is a claim about
what is *running*. Only the second one justifies skipping.

### Alternatives, explicitly rejected

| option | verdict | why |
|---|---|---|
| **(a)** derive the changed set inside the build from the deployed commit (chosen) | **accepted** | Needs no new AWS resources, no webhook change, no state file. Both sides of the comparison are already in the build: the deployed SHA from ECS, the `HEAD` tree from the checkout. It also keeps the build *running* (green commit status) rather than not running at all. |
| (b) a GitHub Actions / webhook-side path filter that never starts the build for docs-only pushes | **rejected** | It cannot satisfy the requirement: a docs-only commit must still finish with a **green commit status**, and a webhook filter that skips the build leaves the commit with no status at all (CodeBuild writes `STARTED`/`SUCCEEDED` through `report_build_status`, and only if a build runs). It also moves the decision to a place with no knowledge of what is deployed, and adds a second trigger surface next to `aws_codebuild_webhook.main` — the thing `pipeline.tf` explicitly warns about (a hand-made/extra hook silently rotting). GitHub `paths-ignore` on a CodeBuild trigger does not exist; the CodeBuild webhook filter grammar has no file-path filter. |
| (c) a marker file (e.g. `.deploy-needed`, or a file recording the last deployed commit) | **rejected** | It is a second source of truth that has to be written by whoever deployed last, so it is wrong exactly when it matters — after a failed or out-of-band deploy — and it fails **open** (a stale marker says "docs only" while production is behind). The deployed commit is already recorded, authoritatively, in the task definition that is running; a marker file only duplicates it with more ways to be stale. It also adds a write to `develop` from the pipeline. |

### The one precondition, and it is an infrastructure attribute

The deployed commit has to exist in the clone for its tree to be diffable. `pipeline.tf` set
`git_clone_depth = 1`, i.e. only `HEAD` — the deployed commit is an ancestor that is **not there**, and
a 12-character tag cannot be fetched by SHA (git needs the full object name). So the source attribute
is part of this change:

```hcl
  source {
    type      = "GITHUB"
    location  = "https://github.com/${var.github_repository}.git"
    buildspec = "buildspec.yml"
    git_clone_depth = 0     # was 1 — full history, so the deployed commit is in the clone
```

`0` means "full history" in the CodeBuild API. The repository is 22 MB and 530 commits, so this costs a
few seconds of `DOWNLOAD_SOURCE`. I did not apply it (§9) — the plan in §4.3 is exactly one in-place
update.

The gate does not *depend* on that attribute being applied: if the clone is shallow it tries
`git fetch --unshallow origin` before giving up, and giving up means a normal full deploy. So the
pipeline is correct before the apply and cheap after it.

### 2.1 The decision, end to end

```
pre_build:
  IMAGE_TAG = ${CODEBUILD_RESOLVED_SOURCE_VERSION:0:12}
  DEPLOY_DECISION=deploy                    # written before anything can fail
  python3 scripts/deploy-scope.py --write /tmp/deploy-scope.env
      aws ecs describe-services   -> PRIMARY per service, rolloutState must be COMPLETED
      aws ecs describe-task-definition -> container image tag per service; all three must agree
      git rev-parse <tag>         -> full SHA (fetch --unshallow once if the clone is shallow)
      git diff --name-only <sha> HEAD
      -> every path inside docs/, evidence/, plan/?  skip : deploy
  source /tmp/deploy-scope.env; anything that is not the literal "skip" becomes "deploy"

build:   unchanged — typecheck, tests, audit gate, three images, push, ECR scan gate

post_build:
  read the decision again, defaulting to deploy
  skip  -> print the live task definitions, register nothing, update nothing, exit 0 (build green)
  deploy-> the original rollout: register 3 revisions, update 3 services, wait, verify, exit 1 on rollback
```

Deliberately **not** skipped: images are still built, pushed and scanned, and migrations still run.
Rationale in §8 — the point of the change is that a docs commit cannot replace a task-definition
revision, and keeping the whole gate chain on every commit means a green build still means what it
meant before.

## 8. Decisions inside the change that a reviewer should see

### 8.1 The allowlist is exactly `docs/`, `evidence/`, `plan/`

Root-level `README.md`, `*.docx`, `QA/`, `docs/`-adjacent markdown all still deploy. That is
conservative on purpose: the acceptance names three directories, and every extra prefix is one more way
for a real change to slip out of a rollout. Widening it is a one-line change (`--allow` default in
`scripts/deploy-scope.py`), and the commit that widens it touches a `scripts/` file, which is outside
the allowlist — so it deploys itself and cannot be self-granting.

### 8.2 Images are still built, pushed and scanned; migrations still run

Only the rollout is conditional. Exiting early before `docker build` would have made the skip cheaper
and made the build prove nothing: the ECR scan gate has nothing to scan without a pushed image, so a
docs commit would go green having skipped the security gates as well. The requirement is that a
docs-only commit completes a build without rolling the services — not that it becomes an empty build.
A cheaper docs path (skip `build` too, and the scan gate with it) is a separate story with its own
trade-off, and is not in this one.

### 8.3 A skipped build still leaves a traceable image

Images for the commit are in ECR tagged with its SHA, and the build log prints the three task
definitions in effect after the skip. So "which commit is production on" stays answerable from ECS, and
"what did this commit build" from ECR.

### 8.4 Concurrency

Two builds can overlap. If a code build is mid-rollout when a docs build evaluates, that docs build
sees `rolloutState != COMPLETED` and does a full rollout too — wasteful, safe, and rare. Two docs
builds skip independently and write nothing, so they cannot race each other at all.

## 9. What I did not do

- **No `terraform apply`.** `pipeline.tf` carries the `git_clone_depth = 1 → 0` change; the plan in
  §4.3 says 0 to add, 1 to change, 0 to destroy, and it is the orchestrator's to apply, once.
- **No deploy, no push to `develop`.** Branch `feat/E15-S7-docs-no-deploy` only.
- **No ECS mutation of any kind** — no task definition registered, no service updated, scaled, stopped
  or deregistered. No ECR push. No IAM, webhook or CodeBuild change.
- **The live two-push proof is not done, and this story is not verified.** The acceptance criterion's
  second half — push a docs-only commit to `develop`, then a code commit, and observe the task-definition
  revisions stay put then move — needs both a push and a real build. That is the orchestrator's (§10).
- **The `git fetch --unshallow` path inside a real CodeBuild container is unproven.** I do not know
  whether the CodeConnections source leaves usable git credentials for a mid-build fetch. Locally the
  fallback works (case `skip/shallow-deepen-works`); in CodeBuild it is untested, and if it does not
  work the gate simply deploys until `git_clone_depth = 0` is applied. This is the reason that
  attribute is part of the change rather than an optimisation.
- **No live `aws ecs` call against the real cluster** to read the deployed tag — that would have been a
  read, but the harness already proves the parsing against the documented response shape, and the
  real run is the orchestrator's proof anyway.
- **`shellcheck` is not installed on this host**, so the shell blocks were checked with `bash -n` only
  (§4.4) plus execution in §6, which is the stronger check.

## 10. For the orchestrator

1. **Apply the HCL** (merge first, then `terraform apply` from the merged tree): one in-place update of
   `aws_codebuild_project.main.source.git_clone_depth` 1 → 0. Do not combine it with anything else —
   it is the only resource in the plan.
2. **Then the live proof**, two pushes to `develop`:
   - a docs-only commit (e.g. a sentence in `docs/ONCALL-RUNBOOK.md`): expect a **green** build, the
     log line `deploy-scope: DECISION=skip`, `=== Build SUCCEEDS with all three services untouched ===`,
     and `aws ecs describe-services` showing the same `taskDefinition` for all three services as before
     the push;
   - a code commit: expect `deploy-scope: DECISION=deploy`, three new revisions, and the verification
     block in `post_build` printing `OK` for api, worker and portal.
3. If the docs push instead shows `DECISION=deploy`, read the `reason:` line — it names the condition
   (usually a stale tag on one service, or the clone could not be deepened because the apply has not
   happened yet), and it is a fail-safe, not a bug in the decision.
