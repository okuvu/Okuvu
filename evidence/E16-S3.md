## 3. The defect: zero allowlist rows (03:34Z → 03:36Z)

`apps/therapist-portal/src/lib/auth.ts` `signIn` callback looks the Cognito email up in
`prisma.therapist` and returns `/auth?error=unauthorized` when it is absent. Against production:

```
$ bash scripts/in-vpc-db-task.sh --sql-file q.sql
# SQL: SELECT json_build_object('count',(SELECT count(*) FROM "Therapist"), ...)
[{"result":{"count":0,"rows":null}}]
```

**The table was empty.** (Two earlier probe queries failed first and are recorded for honesty:
`column "firstName" does not exist` — the Prisma model is snake_case with a `name` column, not
`firstName`/`lastName`; and a two-statement file printed `undefined` because the runner only prints
`result.rows` for a single statement. Both were probe bugs, not app bugs.)

A full login was run before fixing it, to confirm the diagnosis end to end — the Cognito half
worked, the allowlist refused:

```
[2026-10-29T03:32:24Z] step 5: HTTP/2 302
[2026-10-29T03:32:24Z] step 5: location = https://okuvu.in/api/auth/callback/cognito?code=49274b77-a2b1-462a-9b1c-44ffa71799fa&state=jAdUHGZ8wrd5TJOCndazS5MMVZ3zOQWly5m78F8dZXs
[2026-10-29T03:32:27Z] step 6: HTTP/2 302
[2026-10-29T03:32:27Z] step 6: location = /auth?error=unauthorized
[2026-10-29T03:32:27Z] step 7: GET https://okuvu.in/dashboard -> 307 location=/auth
```

Two hops in this chain are easy to get wrong and are worth recording:

- the hosted UI's `<form action>` **carries the OAuth query string** (`client_id`, `redirect_uri`,
  `state`); POSTing credentials to a bare `/login` returns
  `302 /login?null` with a `cognito-fl` cookie containing *"Internal server error, please try
  again"*. Observed at 03:32:09Z, fixed by posting to the parsed `action` URL.
- NextAuth requests `scope=openid` for this provider, yet `profile.email` is still populated (the
  provider reads `/oauth2/userInfo`), so the allowlist check does run — it is not silently skipped.

## 11. Honest list of what is NOT proven here

1. **A human clicking through a browser from a cold start.** The proof is scripted curl for the
   token chain plus a browser render of the resulting session. Every hop is the production hop, but
   no person typed a password into the hosted UI form. (Doing so would have required the password in
   an agent-visible field; the scripted path exercises the same endpoints.)
2. **MFA/TOTP.** `MfaConfiguration=OPTIONAL` and none of the three accounts has TOTP enrolled, so
   the OTP branch of the hosted UI was never exercised. Enrolling a factor would change the shared
   credential the therapists use; left to the onboarding step.
3. **Password reset / rotation flows.** Untested; out of scope for this story.
4. **Client data in the dashboard.** `clients.list` returns `[]` for all three because no client
   assignments exist yet — the dashboard is reachable and authenticated, but the caseload is empty.
   Whose client shows up for whom is E16-S4/E17 work.
5. **`portal.okuvu.in`.** Only `https://okuvu.in` was exercised (the acceptance host). The same task
   serves the alias, but it was not re-verified in this pass.
6. **The ledger row.** `plan/run-ledger.psv` (primary checkout, outside this worktree) still reads
   `E16-S3 … in_review … "STILL BLOCKED on: … upserting the Therapist allowlist rows in-VPC, then a
   browser round-trip."` The orchestrator should set `status=verified`, `branch=feat/E16-S3-therapist-seed`,
