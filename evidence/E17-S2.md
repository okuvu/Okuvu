### 4b. A genuine `ThrottlingException`, injected at the transport layer

A quota-exhausting burst is not cheap or safe here: the published default is 100M tokens/min and
10k requests/min for this model, so provoking a live 429 would mean burning ~100M tokens in a
minute and would throttle the live api/worker for that minute. Instead the throttle response was
injected with a local HTTP/2 stub (the SDK for this version speaks h2c to the endpoint) returning
`429` + `x-amzn-ErrorType: ThrottlingException`, and both the raw SDK call and the **compiled
product module** (`apps/api/dist/lib/bedrock.js`, i.e. what the container runs) were pointed at it.
No model tokens consumed, no quota touched.

Harness (`/opt/data/cache/scratch/e17/throttle_probe.mjs`): `http2.createServer()` on
127.0.0.1:8971 answering every request with


### 4c. What the code does with it — and what the user sees

Call site: `apps/api/src/lib/bedrock.ts:319`
`const response = await getClient().send(new ConverseCommand(input), { abortSignal })`

Error handling: `apps/api/src/lib/bedrock.ts:343-350`

```ts
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    const failureReason: 'timeout' | 'api_error' = timedOut ? 'timeout' : 'api_error';
    console.error({ reason: failureReason, err: message, model }, 'Bedrock call failed');
    return { text: SAFE_FALLBACK, fallbackUsed: true, failureReason, model, canned: false };
  } finally {
    clearTimeout(timer);
  }
```

`SAFE_FALLBACK` is defined at `apps/api/src/lib/canned-response.ts:9`:

```ts
export const SAFE_FALLBACK = "I'm here to support you. Could you tell me more about how you're feeling?";
```

The websocket turn handler then emits that text as the assistant reply and only flags
`fallback_used` in the log (`apps/api/src/routes/websocket.ts:277`); the client is not told why.

**Behaviour, written down:**

1. The SDK retries a 429 itself — 3 attempts total, ~283 ms of backoff for this call — before the
   error reaches product code. There is no `maxAttempts` / `retryMode` override anywhere in
   `apps/api/src`, so the SDK default (standard, 3 attempts) is what production gets.
2. When retries are exhausted the `ThrottlingException` is caught by the same catch-all used for
   every other failure and becomes `failureReason: 'api_error'`.
3. **The user sees the safe fallback sentence** — *"I'm here to support you. Could you tell me more
   about how you're feeling?"* — i.e. a graceful, in-persona, non-technical message. No stack
   trace, no empty bubble, no crash. The turn is not lost; the conversation continues.
4. Throttling is **not distinguishable** from any other Bedrock failure: the same sentence, the same
   `api_error` reason, no "we're busy, try again in a moment" wording, no retry-after handling, and
   a user who is mid-crisis gets a generic reflection instead of their answer. For a mental-health
   product that is a soft failure, not a hard one — but it is a gap: `ThrottlingException` deserves
   its own message and its own metric label. **Recorded as a gap; not fixed here (that is E17-S4).**
5. It is graceful by construction for *any* thrown error, so a throttle cannot take the api down —
   only degrade the reply.

## 7. Unproven / open

1. **Account-applied quota values** — `servicequotas:ListServiceQuotas` and `GetServiceQuota` are
   denied for both identities available in this account. 100,000,000 TPM / 10,000 RPM is the
   published default only; the applied value and both quota codes remain UNVERIFIED. Needs a
   principal with Service Quotas read access (or the console).
2. **A live 429** was never provoked, by design (see §4b). The throttle path was exercised with an
   injected transport-level 429 through the real compiled module; the numbers above describe the
   SDK and product behaviour, not a measured distance-to-quota.
3. **`bedrock-mantle` endpoint quotas** are separate from `bedrock-runtime` per the docs and were
   not examined; the product calls `bedrock-runtime` only.
4. **Worker path** — the same module is compiled into `apps/worker/dist/lib/bedrock.js`; it was not
   run separately, but it shares the identical Converse call and catch-all, and the worker's task
   definition carries the same `BEDROCK_MODEL_ID` / `LLM_PROVIDER=bedrock`.
5. **Documentation drift**: `provider-config.ts:28` says 8K output; the service reports a 32768-token
   maximum. Comment only, not fixed here.
