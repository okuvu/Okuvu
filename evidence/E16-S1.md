## 2. Change — `infrastructure/aws/evia-beta/dns.tf`

Extended the existing `alb` / `alb_ipv6` for_each pattern rather than adding a second one. The new
names are held in their own local so the certificate's `subject_alternative_names` (which is built
from `local.alb_hostnames`) is byte-for-byte unchanged — changing that list would have replaced a
live, ISSUED certificate in use by the ALB.

```hcl
  # The bare brand domain and its www alias. Kept out of local.alb_hostnames on
  # purpose: that list also feeds the certificate's subject_alternative_names,
  # and adding to it would replace the (already ISSUED, already in use) cert.
  apex_hostnames = [
    var.dns_zone_name,
    "www.${var.dns_zone_name}",
  ]

  alb_record_names = concat(local.alb_hostnames, local.apex_hostnames)
```

Both record resources switched from `toset(local.alb_hostnames)` to
`toset(local.alb_record_names)` and gained `allow_overwrite = false`, so a pre-existing record
under any of these names makes the apply fail instead of being silently replaced:

```hcl
resource "aws_route53_record" "alb" {
  for_each        = var.manage_dns ? toset(local.alb_record_names) : toset([])
  name            = each.value
  type            = "A"
  allow_overwrite = false
  alias {
    name                   = aws_lb.api.dns_name
    zone_id                = aws_lb.api.zone_id
    evaluate_target_health = true
  }
}
```

`allow_overwrite = false` was verified by the apply itself: creating `okuvu.in` A succeeded while
the apex already carried MX/NS/SOA/TXT records — Route53 rejects a same-name-same-type replace, not
a different type. No `CHANGED` or `REMOVED` record appears in the diff in §3.

## 4. Blocker found and fixed: the ALB was IPv4-only

Creating the AAAA records was not enough. Every `AAAA` alias in the zone — including the pre-existing
`api.` / `portal.` ones — returned NODATA:

```
$ curl -s -H 'accept: application/dns-json' 'https://cloudflare-dns.com/dns-query?name=api.okuvu.in&type=AAAA'
{"Status":0, ... "Answer" omitted}          # before: no Answer section
$ aws elbv2 describe-load-balancers --names evia-beta-alb --query 'LoadBalancers[0].IpAddressType'
"ipv4"
```

An ALB only answers AAAA when it is dualstack, and a dualstack ALB requires an IPv6 CIDR on the VPC
and on each of its subnets. So, outside `dns.tf` but required by this acceptance criterion:

```hcl
# vpc.tf — Amazon-provided /56, plus one /64 per public subnet
resource "aws_vpc_ipv6_cidr_block_association" "main" {
  vpc_id                           = aws_vpc.main.id
  assign_generated_ipv6_cidr_block = true
}
resource "aws_subnet" "public" {
  ipv6_cidr_block                 = cidrsubnet(aws_vpc_ipv6_cidr_block_association.main.ipv6_cidr_block, 8, each.value)
  assign_ipv6_address_on_creation = true
}
resource "aws_route" "public_internet_ipv6" {          # ::/0 to the existing IGW
  destination_ipv6_cidr_block = "::/0"
  gateway_id                  = aws_internet_gateway.main.id
}
# alb.tf
resource "aws_lb" "api" {
  ip_address_type = "dualstack"
}
```

The ALB security group also gained `ipv6_cidr_blocks = ["::/0"]` on 80/443 — without it the records
would answer but IPv6 connections would be dropped.

Two mistakes this workflow should not repeat:

- `aws_vpc_ipv6_cidr_block_association` needs `assign_generated_ipv6_cidr_block = true`; with only
  `vpc_id` AWS returns `InvalidParameterCombination` and the attribute is `ipv6_cidr_block`, not
  `cidr_block`.
- Adding the association out of band makes the AWS provider report `assign_generated_ipv6_cidr_block`
  / `ipv6_cidr_block` on `aws_vpc` and plan to strip them (which would have disassociated IPv6 and
  broken the ALB). `aws_vpc.main` now has `lifecycle { ignore_changes = [assign_generated_ipv6_cidr_block, ipv6_cidr_block] }`.
