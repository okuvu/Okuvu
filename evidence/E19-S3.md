### Where they came from (no invented identity)

Both files are generated by `docs/store/build-assets.py` from assets already in the app, so
the store art and the launcher art cannot drift apart:

- **Icon** — `apps/mobile/assets/brand/okuvu-appicon-1024.png` (1024×1024, the shipped
  launcher art: purple gradient rounded-square, lavender spiral, marigold dot), downscaled
  with Lanczos to 512.
  The source is a *rounded* square on a transparent field. Play requires a 512×512 32-bit
  PNG and applies its own corner mask, so uploading the rounded art would produce a second,
  mismatched rounded edge on a transparent corner. The corners are therefore filled with the
  icon's own background: a 64×64 grid average of the opaque pixels, nearest-neighbour
  propagated into the empty corner cells, blurred and upscaled — a reconstruction of the
  existing gradient, not a new colour. Verified smooth: the largest channel difference
  between any two adjacent pixels inside the filled region is **1/255** (mean 0.03).
  Measured corner pixels: `(1,1)=(47,18,85)`, `(510,510)=(89,43,138)` — continuous with the
  interior gradient, no seam.
  A first attempt that edge-extended the rows instead left visible horizontal streaks; it was
  discarded, not shipped.
- **Feature graphic** — `apps/mobile/assets/brand/okuvu-mark-dark.png` (the app's own
  light-fill spiral + marigold dot), the app's live palette (`app_colors.dart`:
  violet `#7B6CD9`, lavender wash `#EDE6FB`, oat `#F7F3FD`, plus the icon's own gradient
  endpoints `#34155B` → `#582A8A`), and the app's real typeface Poppins
  (`apps/mobile/assets/fonts/Poppins-SemiBold.ttf`, `Poppins-Regular.ttf`) — the same font
  the UI uses.
  Composition is centred and kept inside Play's cutoff zones: the drawn content box is
  **(241, 148) → (783, 360)**, inside the safe box **(152, 76) → (872, 424)** the build
  script asserts against. The mark is deliberately small (150 px, 30% of the height) rather
  than repeated at icon scale, because Play shows the feature graphic next to the app icon
  and asks that the two not duplicate each other.
  No badge, no ranking, no price, no call-to-action, no testimonial, no screenshot mockup,
  no clinical claim.

Both are reproducible: `python3 docs/store/build-assets.py` regenerates byte-identical
output from the committed inputs.

### Truthfulness checks performed

- **The live privacy policy was read before the copy was written**
  (<https://okuvu.in/privacy>, v1.0 beta, last updated 2026-10-28), and the copy was checked
  line by line against it. One draft sentence was cut because of it: it said the client sees
  "the notes, homework and reminders your therapist has left for you", but §2 of the policy
  states therapist notes are "visible to them, not to you in the app today". The copy now
  claims only appointments, homework and reminders, all of which the Today card and
  appointments screen actually render (`features/home/widgets/today_card.dart`).
- **Every feature claim maps to a shipped screen** — the mapping table is at the end of
  `docs/store/listing-copy.md`, ten rows, each naming a file under `apps/mobile/lib/src/`.
- **No clinical or certification claim anywhere.** The verifier greps for
  `clinically validated`, `clinically reviewed`, `clinically proven`, `medical device`,
  `FDA`, `CE marked`, `therapy app`, `treats`, `cure`, `diagnose`, `HIPAA`, `DPDP compliant`,
  `certified` — none present. The listing says plainly that Okuvu "is not a therapist and is
  not a replacement for professional diagnosis, treatment or emergency care", and points
  someone in danger at emergency services.
- **Audio claim matches §3**: dictation is done by the phone's own recogniser and "Okuvu
  never receives or stores the audio".
- **Privacy policy URL** `https://okuvu.in/privacy` is in the full description, as Play
  requires.
- The copy also states the real access model — accounts are created through a therapist, and
  an un-invited number joins a waitlist (`features/auth/waitlist_screen.dart`, the
  `NO_ACCOUNT` branch of `otp_login_screen.dart`). A listing that implied open sign-up would
  have been false and would have failed review.

## 5. Screenshots — BLOCKED-ON-DEVICE

Zero screenshots exist. None were faked, and none were substituted with mockups, golden
renders or portal screenshots.

Emulator viability was checked rather than assumed, and disproved in four ways:

```console
$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory
$ grep -c -E "(^flags.*(vmx|svm))" /proc/cpuinfo
0
$ nproc; free -m | sed -n 2p
4
Mem:            7941        3664        3517           2        1108        4277
$ ls /opt/data/home/.local/android/emulator
ls: cannot access '/opt/data/home/.local/android/emulator': No such file or directory
$ ls /opt/data/home/.local/android/system-images
ls: cannot access '/opt/data/home/.local/android/system-images': No such file or directory
$ adb devices
List of devices attached
```

No attached device, no emulator package, no system image, no `/dev/kvm`, and a CPU exposing
no virtualisation flags. The Flutter SDK at `~/.local/flutter-sdk` and the Android SDK are
present, so a build is possible; running one is not, because there is nothing to run it on.
Installing the emulator plus an API 36 image (~2 GB) and booting it under full software
emulation on 4 shared cores was judged not viable inside this task's 40-minute budget, and
was not attempted further.

What is committed instead is an executable runbook:
`docs/store/screenshot-capture-plan.md` names the five screens (Home, Chat, Journal, Progress,
Appointments), the exact `adb exec-out screencap -p > raw/01-home.png` commands, the
alternate `screencap` + `pull` form for Windows shells, the demo-account and data-hygiene
rules, and Play's real constraints: 2–8 screenshots, JPEG or 24-bit PNG, 320–3840 px, and a
maximum dimension no more than **twice** the minimum — which is why a raw 1080×2400 capture
(2.22:1) is rejected and must be cropped to 9:16.

`docs/store/finalize-screenshots.py` performs that crop. Its arithmetic is already exercised:
a synthetic 1080×2400 input produced a 1080×1920 `mode=RGB ratio=1.778` output and the script
printed PASS. The synthetic file was deleted; nothing that is not a real app screenshot is
committed under `docs/store/screenshots/`.
