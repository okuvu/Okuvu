## 1. What the client actually does with a safety outcome

Read before writing any test. Four steps, in the order a frame meets them:

| # | File | What it does |
| --- | --- | --- |
| 1 | `apps/mobile/lib/src/core/websocket_service.dart:129` (pre-change; `_onMessage`) | The single JSON dispatch. `AGENT_TURN` → `_handleAgentTurn`; `CRISIS_SIGNAL` → `_crisisSignalController`; `ERROR` is logged and dropped. |
| 2 | `apps/mobile/lib/src/features/chat/models/agent_turn_frame.dart:23` | Reads `payload.message` (falling back to top-level `content`), `turn_id`, `turn_count`, `tool_card`, `journal_prompt_suggested`. **It never reads `payload.safety`.** `content == null \|\| content.isEmpty` throws `FormatException`, and `_handleAgentTurn` catches it and drops the frame. |
| 3 | `apps/mobile/lib/src/features/chat/chat_screen.dart:640` (`_ChatBubble`) | Agent messages render as `Text(message.content)` — no `maxLines`, no `overflow`, no `substring`. The S3/medical/fallback copy reaches the user whole *if* it arrives as `message`. |
| 4 | `apps/mobile/lib/src/features/crisis/crisis_overlay.dart` | The S4 card. Rendered app-wide from `App`'s `builder` Stack (`apps/mobile/lib/src/app.dart:49` `_CrisisOverlaySlot`) whenever `crisisOverlayProvider` is true. Hardcodes the five helplines: iCall `9152987821`, Vandrevala `1860-2662-345`, NIMHANS `080-46110007`, Snehi `044-24640050`, Emergency `112`. |

**Does the client parse the safety codes? No.** Proof (2026-10-30T04:53:23Z, in the worktree):

```
$ grep -rniE "safety_code|safetyCode|CRISIS_FLOOR|MEDICAL_EMERGENCY_FLOOR|SAFE_FALLBACK|SAFETY_UNAVAILABLE|MODEL_UNAVAILABLE" lib
$ echo "grep exit=$?"
grep exit=1
```

There is no `SafetyNotice` model anywhere in the Dart tree. The api sends
`payload.safety = {code, reason, crisis_floor?}` on `AGENT_TURN` and
`CRISIS_SIGNAL` (`apps/api/src/routes/websocket.ts:366`, `:340`), and the client
drops the field on the floor. That is **not** a rendering failure today, and I
did not invent a model for it to sit unused: the whole approach is
"the copy rides `message`, the code is metadata" (`packages/shared-types/index.ts:144-155`),
and every client path below renders `message`. It does mean **no client
behaviour can ever be keyed off a code** — including a future one — so the
tests assert on what is actually promised: the copy arrives, whole and visible.

So the rendering surface is exactly two things: `message` for three of the four
outcomes, and the `CRISIS_SIGNAL` branch for the fourth. Both are now tested.

frames can be fed without a socket:

Full log: `/opt/data/cache/scratch/e17s11/red.log`.

Two failures, one root cause, both safety-relevant:

**Defect — the S4 reply the api sends is thrown away.**

`apps/mobile/lib/src/core/websocket_service.dart:153-157` (pre-fix):

```dart
case 'CRISIS_SIGNAL':
  final crisisPayload = data['payload'] as Map<String, dynamic>?;
  final crisisSessionId = crisisPayload?['session_id'] as String?;
  _crisisSignalController.add(crisisSessionId);   // message discarded
  break;
```

`apps/mobile/lib/src/core/providers.dart:134-136` (pre-fix):

```dart
_crisisSub = ws.crisisSignalStream.listen((_) {
  ref.read(crisisOverlayProvider.notifier).show();   // overlay only
});
```

The api puts the governed crisis copy on that frame deliberately —
"included for audit/transcript continuity" (`packages/shared-types/index.ts:255-262`)
— and persists the same string as the assistant `Turn`
(`apps/api/src/pipeline/fallbacks.ts:214-224`). The client kept only
`session_id`. Consequences, both asserted above:

1. **Dismissing the card leaves the user's last message with no reply under
   it.** The card is dismissible ("I'm safe for now",
   `crisis_overlay.dart:90`). After dismissal the transcript shows the user's
   disclosure and nothing else — the five helplines the server sent are gone
   from the conversation record, on the exact screen the user returns to.
2. **The client then tells a user in crisis their message went unanswered.**
   `ChatScreen` starts a 20s timer when the user sends
   (`chat_screen.dart:34`, `:180`). An assistant message clears it; a
   `CRISIS_SIGNAL` added no message, so the timer ran out and fired
   `No response received. Please try again.` — that is the assertion that went
   red, verbatim. (The snackbar renders under the full-screen card, so it was
   invisible while the card was up and appeared the moment the user dismissed
   it.)

Everything else the api can send already rendered correctly — the S3 grounding
copy, the medical floor, both degraded copies, `SAFE_FALLBACK` with and without
a notice, and an unrecognised code all passed before any fix. That is worth
stating plainly: **the chat bubble was not the problem, the crisis branch was.**

## 4. The fix (smallest change that closes both)

`git diff --numstat` of the production files: `+59 / -7` across
`providers.dart` (25/2) and `websocket_service.dart` (34/5), 7 hunks, plus 5/1
in the `home_screen_test.dart` fake:

- `websocket_service.dart` — carry the whole frame instead of one field:
  a 10-line `CrisisSignal {sessionId, message}` value class, the controller and
  the stream typed to it, and `CRISIS_SIGNAL` now reads `payload.message`
  (absent → `''`, so an older server still works).
- `providers.dart` — `ChatNotifier` appends that message to the transcript as an
  assistant message (deduped by `crisis-<session_id>`) **before** showing the
  overlay. No new copy is invented client-side; the only string ever rendered is
  the server's.
- `websocket_service.dart` — `@visibleForTesting handleRawFrame()` seam, which is
  what lets the tests drive the real `_onMessage` switch with no socket.
- `test/home_screen_test.dart` — the `implements WebSocketService` fake gets the
  two signature updates the change implies (stream type, seam no-op).

Side effect worth naming: because a transcript message now exists, `ChatScreen`'s
existing "agent replied → stop typing" listener clears the spinner and cancels
the 20s timer. The `No response received` snackbar can no longer fire for a
crisis turn. That is asserted directly rather than assumed.

Nothing else was changed. In particular no helpline list, no copy, and no
clinical wording was touched anywhere in the client.

## 6. What each test asserts

`apps/mobile/test/features/safety/safety_route_rendering_test.dart` — 13 tests.
Every frame is built in the shape `apps/api/src/routes/websocket.ts` writes and
fed through `WebSocketService.handleRawFrame` → real `jsonEncode`d JSON → real
`_onMessage` → real notifier → real widget tree. No dio call, no socket.

The shared assertion `expectVisibleAndComplete(tester, string)` is the core of
the file. It fails unless: exactly one `Text` holds the string; `maxLines` is
null; `overflow` is not ellipsis; the laid-out `RenderParagraph`'s plain text is
**character-for-character equal** to the server string (not a prefix); the
paragraph has height; and the paragraph's rect starts inside the viewport.

**S4 crisis (`CRISIS_SIGNAL`)**
1. A frame carrying `CRISIS_RESPONSE` shows the card: `You're not alone.`, all
   five names, all five numbers — each asserted as visible, untruncated text,
   and each number additionally asserted present in the joined rendered
   paragraph text (a number that only exists as a `tel:` argument would fail).
   Also asserts `crisisOverlayProvider` flipped and that nothing was on screen
   before the frame, so the frame is what put it there.
2. The same frame with `safety: {code: CRISIS_FLOOR, reason: llm_timeout,
   crisis_floor: true}` shows the same card — the floor notice neither hides nor
   breaks it.
3. **After dismissing the card** the api's crisis copy is still in the
   transcript, rendered in full. *(red before the fix)*
4. A crisis turn settles the pending turn: typing indicator gone, and after
   pumping 21 s the `No response received. Please try again.` snackbar is absent.
   *(red before the fix)*

**S3 grounding (`AGENT_TURN`, no safety notice)**

5. The 585-char grounding copy renders in full; the helpline digits survive as
   text (`9152987821`, `1860-2662-345`), the labelled forms
   (`iCall on 9152987821`, `Vandrevala Foundation on 1860-2662-345`) survive, and
   so does the closing `I'm here with you.` — i.e. nothing is clipped at either
   blank line.

**Medical emergency (`AGENT_TURN`, `MEDICAL_EMERGENCY_FLOOR`)**

6. The 327-char floor copy renders in full, `112` present, and the paragraph
   **starts with** `Please call 112 for emergency medical help right now`.
7. The crisis-overlap variant renders in full and keeps `112` *and* both
   helplines.

**Degraded (`AGENT_TURN` with a notice)**

8. `SAFE_FALLBACK` text with `{code: MODEL_UNAVAILABLE}` renders in full.
9. The same text with **no** `safety` field at all (older server / canned path)
   renders in full.
10. `SAFETY_UNAVAILABLE` and `MODEL_UNAVAILABLE` copies render in full, in one
    transcript, with their helpline digits intact.

**Unknown / absent**

11. `{code: 'SOMETHING_ADDED_IN_2027'}` — an outcome this build has never seen —
    renders the message in full, and the transcript holds exactly one non-empty
    assistant message. No empty bubble.
12. The E17-S6 budget-refusal frame (`turn_id: null`, `budget` absent here)
    renders its copy and helplines.
13. A safety notice with **no message** never produces an empty bubble: no
    zero-content assistant message reaches the transcript. (Current behaviour is
    to drop the malformed frame and let the turn time out with the existing
    snackbar. Recorded as behaviour, not celebrated — see §8.)

## 7. What these widget tests cannot prove

Stated plainly, because a green run here is easy to over-read:

- **Nothing about a real device or a real socket.** `handleRawFrame` is the same
  `_onMessage` a socket read calls, so the parse/dispatch is real, but the
  transport, TLS, auth headers, reconnect and the 10 s connect timeout are not
  exercised. Nothing here proves the app connects, only what it does with a frame
  once it has one.
- **Nothing about what the api actually sends in production.** The fixtures are
  the api's source constants at this commit; if the deployed service serves
  different copy, these tests still pass. The api side is E17-S4/S9/S10's
  evidence, not this file's.
- **Nothing about how it looks.** No golden images, no contrast/overflow audit of
  the crisis card at real font scales, no accessibility labels, no Dynamic Type
  or large-text layout. A paragraph that lays out at 1080x2400 in Roboto may
  still overflow on a 360dp-wide device at 200% text scale. "Laid out with
  height > 0 and starting inside the viewport" is not "readable by a human".
- **Nothing about audio.** TTS is stubbed in these tests. Whether the crisis copy
  is spoken, cut off, or silent on a device with voice enabled is untested —
  and note the fix deliberately does **not** route the crisis message to TTS
  (only `_onAgentTurn` speaks), so a voice-on user hears nothing for the S4 turn.
  That is a product decision left open, not a verified behaviour.
- **Nothing about `tel:` dialling.** The crisis card's call buttons were not
  tapped; `url_launcher` is a plugin channel with no device here.
- **Nothing about the crisis card's timing versus the network.** Whether the card
  appears before or after an in-flight turn completes, or how it behaves on
  reconnect mid-crisis, is not modelled.
- **Nothing about persistence.** The transcript lives in memory for the tree's
  lifetime; whether the S4 message reloads on app restart is a server/session
  question this file does not touch.
- **Not the real `WebSocketService` state machine.** `FrameDrivenWebSocketService`
  overrides `connect`/`disconnect` to no-ops. `_setState`, `SESSION_OPEN_CONFIRMED`,
  the `_onMessage` switch, the JSON parse, the notifier and the widgets are all
  real, but reconnect/backoff/idle-timeout paths are not.

## 8. Left open (not fixed here)

- **`payload.safety` is still unparsed.** No `SafetyNotice` model in the client.
  Rendering does not need it; a future "show a degraded-turn badge" or "offer
  Call 112" affordance would. Deliberately not built as dead code.
- **A safety notice with no message is dropped**, and the user gets the generic
  "No response received. Please try again." after 20 s. Dropping a frame the
  client cannot render is defensible (there is no copy to show and inventing
  clinical copy client-side is worse), but it is a silent failure. If the
  contract ever allows `message` to be empty, the client needs a governed local
  line — which is a clinical-copy decision, not one for this story.
- **The S4 transcript entry is not spoken by TTS** (see §7).
- **No golden/widget screenshot** of the crisis card or of the S3 bubble at
  realistic device sizes; blocked on the same no-device constraint.
