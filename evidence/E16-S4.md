## 7. Defect found: runtime TLS to RDS fails with `sslmode=require`

The worker's `/health` (a trivial `SELECT 1`) reported `db:"unreachable"` reproducibly, long after
startup:

```
$ scripts/in-vpc-db-task.sh -- 'node -e "fetch(\"http://worker.evia-beta.local:8080/health\")…"'
worker_health_http 200 {"status":"ok","db":"unreachable","timestamp":"2026-10-28T19:23:13.700Z"}
worker_health_http 200 {"status":"ok","db":"unreachable","timestamp":"2026-10-28T19:36:11.971Z"}
```

Reproduced directly with the runtime URL that the ECS task injects from
`evia-beta/database:database_url`:

```
$ scripts/in-vpc-db-task.sh -- <pg + Prisma probe using $DATABASE_URL>
pg_raw FAIL: self-signed certificate in certificate chain
prisma FAIL: Invalid `prisma.$queryRaw()` invocation: Raw query failed. Code: `N/A`.
             Message: `Error opening a TLS connection: self-signed certificate in certificate chain`
```

Cause: `pg` (v8.16+, this repo pins `pg@8.22`) now treats `sslmode=require` as **verify-full**, and
the RDS certificate chain is not in the runtime image's trust store. The Prisma *CLI* (used by
`prisma migrate deploy`) still applies libpq semantics, which is why migrations succeeded while
every runtime query failed. The api's boot check logs "Database connection established" because the
driver-adapter connect is lazy, and `GET /health` never touches the database — so the api looked
healthy while being unable to read anything.

Fix committed in this branch: `apps/api/src/lib/prisma.ts` and `apps/worker/src/lib/prisma.ts` now
normalise the URL by adding `uselibpqcompat=true` when `sslmode=require`, which restores libpq
semantics in the pg driver (connection stays encrypted, chain not verified). The exact rewrite
logic, executed inside the live image against the live secret, at 19:27Z:

```
rewritten_url_params: postgresql://<creds>@evia-beta-postgres…:5432/evia?sslmode=require&uselibpqcompat=true
PRISMA_OK tool_registry_rows=5
```

Verification status: typecheck clean (`tsc --noEmit` 0 errors in api and worker, after
`prisma generate`), unit tests green (api 65 files / 1157 tests, worker 8 files / 92 tests). The fix
is **not deployed**: it reaches production only with the next `develop` build, so the live worker
still reports `db:"unreachable"` at the time of writing. Until that build lands, chat turns,
summaries and every other DB read are failing in production regardless of schema state.

Also fixed, as a latent landmine rather than a live bug: `infrastructure/aws/evia-beta/secrets.tf`
still rendered `database_url` with a literal `***` password (while its own comment claimed
otherwise — the live secret had been corrected by hand). The next `terraform apply` would have
written the redacted URL back and broken container auth completely. It now interpolates
`random_password.db_password.result`. No `terraform apply` was run.

Not fixed here: `apps/therapist-portal/src/lib/prisma.ts` builds its pool the same way and has the
same defect — it needs the same eight-line normalisation (or a shared helper), which belongs to the
portal story.

## 9. What is **not** proven here

1. **Prod itself migrating from empty.** The production database was already at 43/43 when the
   window opened. The empty-database clause is proven on `evia_migrate_verify` (created empty,
   migrated, dropped). Re-running it against prod would have required dropping the schema, which
   the story forbids.
2. **The TLS fix live in production.** Committed and unit-verified, but not deployed. The running
   worker still answers `db:"unreachable"`, so the api's A13/A15 paths cannot work yet.
3. **Therapist portal database access.** Same `sslmode=require` defect, untouched here.
4. **Certificate verification.** The fix restores encryption without chain verification. Real
   hardening (bundle the RDS CA and use `sslmode=verify-full`) is a follow-up, tracked in
   §7.
5. **Developer seed (`packages/prisma/seed.ts`).** Not run against beta by design; only the
   migration-embedded approved-technique and crisis-resource seeds are present.
6. **Snapshot restore.** Out of scope — that is E16-S6. `evia-beta-premigrate-202610281906` is the
   identifier to restore.
