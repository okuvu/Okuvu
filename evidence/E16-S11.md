# E16-S11 — No personal data in log output

Story, verbatim: *"A 24-hour CloudWatch scan across all three services finds zero therapist or client
email addresses and zero personal names, run by a committed scanner script whose pattern set is
documented and which fails rather than warns."*

Branch `feat/E16-S11-log-pii`, worktree `/opt/data/okuvu/wt/E16-S11`, base `origin/develop` @ `6938d70`.
Account `562654496378`, region `ap-south-1`. All timestamps UTC. Commands run from this host on
**2026-10-29 between 05:27Z and 05:42Z**.

**Redaction policy in this file:** no address, phone number or personal name appears below. Addresses
are shown as `a***o@o***u.in`, names as `An******ao`, numbers as `+**********10`. Raw log lines were
never written to a file in this repo; the scanner's samples are its own redactions.

## 1. What was leaking

14-day baseline, measured before any change (`aws logs filter-log-events`, all three groups):

* `/ecs/evia-beta/portal` — 24 events carrying a full therapist address, from
  `apps/therapist-portal/src/lib/auth.ts` lines 52 and 55:
  `[AUTH] Successful sign-in: <address>` and `[AUTH] Unauthorized sign-in attempt: <address>`.
  In this product the address is the person's name, so this is direct personal data.
* `/ecs/evia-beta/api` — 2 events carrying three therapists' full names, addresses and internal ids,
  produced by `scripts/in-vpc-db-task.sh --sql` printing `result.rows` from
  `scripts/seed-beta-therapists.sql` (`RETURNING email, id, name, created_at`).
* `/ecs/evia-beta/worker` — nothing.
* Journal, note and turn bodies, phone numbers: zero in the baseline.

## 2. What changed

| File | Change |
|---|---|
| `apps/therapist-portal/src/lib/log-identity.ts` (new) | `identityRef(kind, value)` → `<kind>_` + 12 hex of `HMAC-SHA256(NEXTAUTH_SECRET, normalised value)`. Stable per value, not reversible without the key. `redactEmails(text)` replaces addresses inside an arbitrary string with their refs. |
| `apps/therapist-portal/src/lib/auth.ts` | Success logs `therapist=t_<12hex>` (ref of the therapist row id); refusal logs `ref=u_<12hex>` (ref of the attempted address). Sign-in outcomes, redirects and the allowlist lookup are unchanged. |
| `apps/therapist-portal/src/lib/email.ts` | Invite mailer logs `toRef=c_<12hex>` instead of the recipient address; a Brevo error body is passed through `redactEmails` and capped at 500 chars. The invite code is still logged (not personal data; it is how a keyless local send is completed). |
| `apps/api/src/lib/log-identity.ts` (new) | Same helper, keyed on `WORKER_INTERNAL_AUTH_SECRET` (already injected into the api task), falling back to `NEXTAUTH_SECRET`, then a per-process random key. |
| `apps/api/src/lib/email.ts` | Both mailers log `toRef` instead of `to`; both Brevo error bodies are redacted before logging. |
| `apps/api/src/agents/a2/agent.ts` | Four logs that carried model output / user-facing text now log `chars` (length) only: S-07 parse failures, fallback parse failure, missing S-07 block, improvised signal marker. `docs/AGENT-CODE-STANDARD.md` §7 forbids logging message text or model output; these were violations of the repo's own standard. |
| `apps/api/src/agents/a9-post/agent.ts` | Same: `raw: resultText` → `chars: resultText.length` on the two fail-closed paths. |
| `scripts/redact-probe-rows.js` (new) | Walks probe result rows: values under email/name/phone/address columns become `<redacted:<column>>`, any embedded address or international number inside other strings is replaced, ids and timestamps are kept. |
| `scripts/in-vpc-db-task.sh` | The `--sql` runner base64-ships the redactor into the probe container and prints `scrub(r.rows)` instead of `r.rows`. |
| `apps/therapist-portal/src/__tests__/log-pii.test.ts` (new) | 11 tests; see §5. |
| `scripts/log-pii-scan.py` (new) | The scanner; pattern set documented in its docstring (also `--list-patterns`). |

Debugging a failed sign-in still works, without the log holding an address: recompute the ref for a
suspected address and compare (the command is in `log-identity.ts`'s docstring). Repeat attempts by one
identity produce one ref, so the correlation a log line was for is preserved.

## 3. Pattern set (committed, documented in the script docstring)

```
email-address    [A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}
phone-e164       (?<![\w+])\+\d[\d \-().]{6,18}\d(?![\w])      # kept only at 8-15 digits
phone-in-e164    (?<![\w.+-])(?:91)?[6-9]\d{9}(?![\w.])       # bare Indian mobile
person-name      seeded therapist names + their bare tokens, case-insensitive
client-name      --client-names pairs (empty by default)
journal-text     --journal-canary substrings (empty by default)
note-text        --note-canary substrings (empty by default)
```

Groups: `/ecs/evia-beta/api`, `/ecs/evia-beta/worker`, `/ecs/evia-beta/portal`. Window: `--hours` or
`--start`/`--end`. Exit codes: `0` clean, `1` any hit, `2` the scan itself could not run. There is no
warn mode and no suppression list.

## 5. Deployment status — why there is no live clean 24 h scan

* The running portal is **pre-fix**: service `evia-beta-portal` runs task definition revision **18**,
  image `…/evia-beta/portal:4c8809bdaa9d`, deployed **04:20Z** — before this commit (`05:37:17Z`).
* That image can only be replaced by a build: `docker info` fails on this host and there is no
  `podman`/`buildah`, so `scripts/deploy-beta.sh` and `buildspec.yml` cannot be run here; the remaining
  path is a CodeBuild run from a pushed branch, and this story is explicitly forbidden from pushing.
* Consequence: **no post-fix live scan exists, and a "clean 24 h scan" cannot exist until 24 h after a
  deploy** — CloudWatch keeps the old events, so any 24-hour window that reaches back before the deploy
  will keep reporting them. The honest acceptance run is: deploy, then
  `scripts/log-pii-scan.py --start <deploy time>` and, 24 h later, `--hours 24`.

Unit-level proof that the new code cannot emit an address, run at `05:34Z` on the commit:

```
$ cd apps/therapist-portal && npx vitest run src/__tests__/log-pii.test.ts
 ✓ 11 tests passed
```

The tests assert, against the real `authConfig.callbacks.signIn` and the real mailer:

* a successful sign-in logs exactly one line, matching `therapist=t_[0-9a-f]{12}`, and that line
  contains no address-shaped text, no `ananya.rao`, and not even the domain `okuvu.in`;
* two sign-ins by the same therapist log the identical line (the ref is stable);
* a refused sign-in logs `ref=u_[0-9a-f]{12}` and no address;
* two different refused identities log two different refs;
* the DB-error path emits no address;
* `identityRef` is deterministic, case/whitespace-normalising, and differs across kinds and values;
* `redactEmails` removes addresses from a provider payload and leaves clean text alone;
* `sendInviteEmail` with no API key logs `"toRef":"c_[0-9a-f]{12}"` and no recipient address.

## 6. Sweep — every log call in api, worker and portal was read

Fixed (6 sites): portal `auth.ts` ×2, portal `email.ts` ×2 log fields (+ error body), api `email.ts` ×2
log fields (+ 2 error bodies), a2 ×4, a9-post ×2, plus the probe script.

**Deliberately left, with reasons:**

1. `apps/therapist-portal/src/scripts/seed-*.ts` — `Seeded: <address>`, `Therapist seeded: <address> (<id>)`,
   `Assigned <id> -> <address>`. These are operator CLI scripts whose whole job is to echo back what was
   just seeded; masking the address would make them useless for confirming a batch, and they are not on
   any request path. The vector that actually leaked (running SQL inside the probe task) is closed in
   `in-vpc-db-task.sh`. Anyone piping a seed script through `in-vpc-db-task.sh --` would still emit its
   output, and that is not detectable from this story.
2. `[AUTH] DB error during sign-in: <error>` (portal `auth.ts`), `Unexpected error on idle Postgres client`
   (all three apps) — the objects logged are driver/pool errors; Prisma's `findUnique` failures carry the
   constraint *name*, not the queried value. Covered indirectly by the DB-error test, which asserts no
   address is emitted on that path.
3. `[email] … invite code logged only { inviteCode }` — an invite code is a short-lived onboarding
   credential, not personal data, and is the one thing that makes a keyless local send completable.
4. `apps/api/src/lib/rate-limit.ts` logs `{ err, key }` where `key` is `ws_turn:<user uuid>` — an internal
   id, not personal data.
5. `apps/test-harness/**` — a separate app, not one of the three services in scope; its seeders log
   addresses the same way the portal seeders do.
