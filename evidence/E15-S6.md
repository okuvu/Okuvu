### 2.1 What existed (and why it could not cover the worker)

All three are ALB metrics keyed on a target group. `evia-beta-worker` has no load balancer (it is
reached through Cloud Map at `worker.evia-beta.local`), so no ALB metric exists for it at all, and
even api/portal were only covered for *health behind the ALB*, not for "the task is gone".

### 2.2 Decision: Container Insights, because it is already on and already paying

Container Insights is **not a new cost here** — it is enabled on the cluster today:

```
$ aws ecs describe-clusters --clusters evia-beta --include SETTINGS --query 'clusters[0].settings'
[
    {
        "name": "containerInsights",
        "value": "enabled"
    }
]
```

(`--include SETTINGS` matters: without it the API returns `settings: []` and this looks disabled.)

The metrics are live, per service, and carry the dimensions the alarm needs:

```
$ # aws cloudwatch get-metric-statistics --namespace ECS/ContainerInsights --period 300
api    RunningTaskCount: 1.0   DesiredTaskCount: 1.0
worker RunningTaskCount: 1.0   DesiredTaskCount: 1.0
portal RunningTaskCount: 1.0   DesiredTaskCount: 1.0

$ aws cloudwatch list-metrics --namespace ECS/ContainerInsights | ... 'metric streams:', len(...)
metric streams: 108
```

Cost of the three options considered, at ap-south-1 list prices:

| option | new monthly cost | robustness |
|---|---|---|
| **alarms on Container Insights** (chosen) | **$0.30** (3 × $0.10 alarm) | managed metric, no code path to break; `RunningTaskCount`/`DesiredTaskCount` already publishing for all 3 services |
| EventBridge task-state-change → Lambda → custom metric | ~$0.90 metric + ~$0.20 Lambda | cheapest on paper, but adds a function, an IAM role and an invoke path that cannot be verified without an apply; a publisher that silently stops looks exactly like a healthy service |
| Logs metric filter on the worker group | ~$0.30 | **cannot work**: the failure mode is "the task is gone", and a gone task writes no log line (see the quiet-idle evidence in section 1) |

Container Insights itself is *not* free, and it was already being paid before this story: 108 metric
streams × $0.30/metric-month ≈ **$32.40/mo**, and it is missing from `cost-model.py`'s total. That is
recorded here rather than acted on — see section 7 for the follow-up it deserves.

### 2.3 What was added

`infrastructure/aws/evia-beta/observability.tf`, one alarm per service, `for_each` over a map of the
desired counts so the threshold tracks `var.*_desired_count` instead of a hard-coded 1:

```hcl
locals {
  desired_task_counts = {
    api    = var.api_desired_count
    worker = var.worker_desired_count
    portal = var.portal_desired_count
  }
}

resource "aws_cloudwatch_metric_alarm" "service_running_tasks_low" {
  for_each = local.desired_task_counts

  alarm_name        = "${var.name_prefix}-${each.key}-running-tasks-low"
  alarm_description = "${each.key} is running fewer tasks than desired (${each.value}); …"

  namespace   = "ECS/ContainerInsights"
  metric_name = "RunningTaskCount"
  statistic   = "Average"

  period              = 60
  evaluation_periods  = 3
  datapoints_to_alarm = 3
  threshold           = each.value

  comparison_operator = "LessThanThreshold"
  treat_missing_data  = "breaching"

  dimensions = {
    ClusterName = aws_ecs_cluster.main.name
    ServiceName = "${var.name_prefix}-${each.key}"
  }

  alarm_actions = [aws_sns_topic.ops_alerts.arn]
  ok_actions    = [aws_sns_topic.ops_alerts.arn]
}
```

Three design choices worth defending:

- `treat_missing_data = "breaching"`. The metric is published by an agent *inside* the task. Zero
  running tasks means zero datapoints — the incident, not a gap. `notBreaching` would hide exactly
  the case this alarm exists for.
- 3 × 60 s, not 1 × 60 s. The worker deploys at `minimumHealthyPercent = 0`, so it legitimately
  dips to zero tasks for a minute during a rollout. Three consecutive breaching minutes alarms on a
  real outage in 3 minutes and ignores a deploy.
- alarm *and* ok actions on the same topic, so recovery is as visible as failure.

## 3. Gap — no ALB access logs (audit trail)

Before:

```
$ aws elbv2 describe-load-balancer-attributes --load-balancer-arn …/app/evia-beta-alb/b206473f7e05ebc2 \
    --query 'Attributes[?starts_with(Key,`access_logs`)]'
[
    { "Key": "access_logs.s3.enabled", "Value": "false" },
    { "Key": "access_logs.s3.bucket",  "Value": "" },
    { "Key": "access_logs.s3.prefix",  "Value": "" }
]
```

Aggregate metrics only: no per-request record of client IP, path, status, bytes or latency. For a
health product that is a DPDP audit-trail hole — an access request or an incident review has nothing
to reconstruct from.

Added (all in `s3.tf`, plus the `access_logs` block in `alb.tf`):

- `aws_s3_bucket.alb_logs` — `evia-beta-alb-logs-562654496378`, same region as the LB (an ALB only
  accepts a bucket in its own region).
- `BucketOwnerEnforced` ownership, all four public-access blocks on, SSE-**S3** (`AES256` + bucket
  key), 90-day lifecycle expiry with abort-incomplete-multipart at 7 days.
- Bucket policy granting `s3:PutObject` to `logdelivery.elasticloadbalancing.amazonaws.com`, scoped
  to `arn:aws:s3:::<bucket>/alb/AWSLogs/562654496378/*`. The prefix is a single `local.alb_access_log_prefix`
  used by both the policy and the `access_logs` block, so the write path and the grant cannot drift.
- `access_logs { bucket = …, prefix = "alb", enabled = true }` on `aws_lb.api`, with
  `depends_on = [aws_s3_bucket_policy.alb_logs]` — `ModifyLoadBalancerAttributes` fails with
  "Access Denied for bucket" if the policy is not attached yet, and the bucket name alone does not
  imply that ordering.

Two deliberate non-choices:

- **SSE-S3, not the customer-managed data key.** ELB cannot be granted `kms:GenerateDataKey`
  through a bucket policy alone, and a KMS grant that fails closed means logs silently never appear.
  AES-256 at rest is the correct trade for access logs.
- **No `aws:SourceAccount` condition on the log-delivery statement.** The `logdelivery.*` service
  principal does not reliably carry that key; a condition that never matches fails closed. The
  resource path is already account-scoped, and the policy matches AWS's documented example
  (Amazon S3 User Guide → "Grant access to Application Load Balancer for enabling access logs").

Rendered policy document (from a throwaway `terraform plan` of the same `aws_iam_policy_document`
with literal values — Access Analyzer's `ValidatePolicy` is not permitted for this role, so this is
the terraform-rendered JSON rather than an API opinion):

      "Resource": "arn:aws:s3:::evia-beta-alb-logs-562654496378/alb/AWSLogs/562654496378/*" },

## 9. Findings outside this story's scope (not fixed here)

1. **Task-definition state drift.** Terraform state holds revisions 10 and provider-normalised empty
   arrays; the services run 18/18/16. Every plan wants to replace all three task definitions. Root
   cause is that images were pinned by the build pipeline (`scripts/ecs-image-pin.py`) rather than
   through terraform, so state never saw revisions 11–18. A `terraform import` of the live revisions
   (or a one-off `-refresh-only`) would settle it. E15-S6 only makes sure the replacement is a no-op
   on content.
2. **`/aws/rds/instance/evia-beta-postgres/postgresql` has no retention** (`retentionInDays: None`).
   Postgres logs are kept forever — unbounded growth and unbounded retention of query text. It is
   created implicitly by `enabled_cloudwatch_logs_exports`, so setting retention needs an `import`;
   doing it blind would fail the apply.
3. **`api` is logging `SQL_ERROR: column "firstName" does not exist`** (2026-10-29T03:32:07Z). A
   real application error, visible precisely because the log group works.
4. **`worker` logs nothing while idle** — no heartbeat, so logs alone can never prove it is alive.
   The running-count alarm covers it; a periodic health probe would make the logs useful too.
5. `terraform fmt -check` reports pre-existing drift in `secrets.tf` (unrelated alignment). Left
   alone to keep this diff to the story.
