## 1. Where the version actually comes from

`apps/mobile/android/app/build.gradle` does **not** hardcode a version. It reads
`flutter.versionCode` / `flutter.versionName` from `android/local.properties`, which
the Flutter Gradle plugin regenerates from `apps/mobile/pubspec.yaml` on every build.
So `pubspec.yaml` is the real single source of truth; editing `build.gradle` would have
been overwritten.

```diff
$ git diff -- apps/mobile/pubspec.yaml
diff --git a/apps/mobile/pubspec.yaml b/apps/mobile/pubspec.yaml
@@ -1,7 +1,7 @@
 name: okuvu
 description: Okuvu — AI Mental Wellness Companion
 publish_to: 'none'
-version: 1.0.4+5
+version: 1.0.5+6
```

The proof that this edit reached the artefact is section 5 (read back out of the `.aab`),
not the edit itself.

## 2. Signing wiring — used the pattern already in the repo, no new mechanism

`android/app/build.gradle` already contained the whole mechanism:

```groovy
def keystorePropertiesFile = rootProject.file('keystore.properties')
...
def hasReleaseKeystore = keystorePropertiesFile.exists() &&
        keystoreProperties['storeFile'] != null &&
        project.file(keystoreProperties['storeFile'].toString()).exists()

signingConfigs {
    if (hasReleaseKeystore) {
        release {
            keyAlias keystoreProperties['keyAlias']
            keyPassword keystoreProperties['keyPassword']
            storeFile file(keystoreProperties['storeFile'])
            storePassword keystoreProperties['storePassword']
        }
    }
}
```

No Gradle change was needed or made. The only action was to create the gitignored
file that this block reads: `apps/mobile/android/keystore.properties`, mode `0600`,
populated from AWS Secrets Manager secret `evia-beta/android-upload-keystore`
(`storePassword`, `keyPassword`, `keyAlias=upload`, `storeFile`). **Password read from
Secrets Manager successfully** — values are not reproduced anywhere in this file.

## 7. What this proves

- `pubspec.yaml` now says `1.0.5+6`, and the built bundle reports `versionCode=6`,
  `versionName=1.0.5` — the version source edit demonstrably reached the artefact.
- The release bundle is signed by the E18-S1 upload key, not the placeholder, proven from
  the bits in `META-INF/UPLOAD.RSA` of the bundle.
- Signing is wired through the repo's pre-existing `android/keystore.properties` mechanism;
  the password lives only in the gitignored local file (mode 0600) and in Secrets Manager.
- Nothing keystore-related is tracked by git.

## 8. What this does NOT prove / not done

- **No upload to Play.** E18-S3 owns the store/API wiring. This bundle is a signing/version
  proof artefact, not a store-ready release candidate: it is the `prod` flavour built with
  **no prod dart-defines**, so whatever the default API config is, it is unchanged from
  `develop`.
- The `.aab` carries a **v1 JAR signature only** (`META-INF/UPLOAD.RSA`/`.SF`); that is
  normal and sufficient — Play re-signs with the app-signing key on upload, and the upload
  key's job is exactly this. No `apksigner`/v2/v3 verification of a release APK was done
  because no release APK was built.
- `jarsigner` reports the self-signed chain as "invalid PKIX path" — expected for a
  self-signed upload certificate with no CA; the signature itself verifies (`jar verified`).
- No offline backup of the keystore/password was made (human-owned, carried over from E18-S1).
- One OOM-killed build attempt is documented above; the workaround was retrying under
  memory headroom, not changing build config.
