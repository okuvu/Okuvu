## 2. Schema: every child of `User` now cascades

`packages/prisma/schema.prisma` — all 18 relations to `User` gained `onDelete: Cascade`. New migration
`packages/prisma/migrations/20261029120000_deletion_cascade_on_user/migration.sql`, generated with

```
$ npx prisma migrate diff --from-schema <pre-change schema> --to-schema packages/prisma/schema.prisma --script
```

which emitted 18 `DROP CONSTRAINT` / `ADD CONSTRAINT … ON DELETE CASCADE ON UPDATE CASCADE` pairs — the
constraint names match the live catalog exactly (§1). The committed file uses `DROP CONSTRAINT IF EXISTS`
so it is re-runnable if a name ever drifts.

**The migration is NOT applied to any database.** It must be applied by whoever owns the environment
(`prisma migrate deploy`) — the erasure path does not depend on it (the tombstone row is retained, so no
cascade ever fires on this flow); it exists so a future hard-delete cannot leak a clinical record.

Validated without touching production: the whole migration, plus a catalog check, inside one transaction
that is then rolled back.

```
$ node in-vpc check (BEGIN; <migration.sql>; SELECT …; ROLLBACK;)
MIGRATION_APPLIES {"cascade":"18","restrict_":"0"}
$ bash scripts/in-vpc-db-task.sh --sql "SELECT count(*) FILTER (WHERE confdeltype='r') AS still_restrict,
    count(*) FILTER (WHERE confdeltype='c') AS cascade FROM pg_constraint
    WHERE confrelid='\"User\"'::regclass AND contype='f'"      # after the rollback
[{"still_restrict":"18","cascade":"0"}]
```

## 3. The erasure path

`apps/api/src/lib/account.ts`:

- one `prisma.$transaction(async (tx) => …)` with `{ maxWait: 10s, timeout: 60s }` — 5s (the default) is
  not enough for a subject with a long `Turn` history, and a half-applied erasure is not erasure;
- ordered deletes, children first: `GovernanceLog` (by the subject's session ids) → `Reminder` (by
  `user_id` **or** `homework.client_user_id`, because `Reminder.homework` is `ON DELETE SET NULL` and would
  otherwise orphan) → `UserToolPreference` → `JournalEntry` → `MoodLog` → `EmergencyContact` →
  `UserMemory` → `EngagementProfile` → `SafetyState` → `ClinicalConfig` → `TherapistNote` →
  `ClinicalAccessLog` → `Appointment` → `InviteToken` → `TherapistClient` → `Homework` → `Turn` →
  `SessionSummary` → `SessionLog` → `BetaConsent` → `WaitlistEntry`;
- `BetaConsent` matches `user_ref IN (id, email, auth_subject)`; `WaitlistEntry` matches only identifiers
  that are actually present — an empty value is never turned into `IS NULL`, which would match rows
  belonging to everybody else;
- the per-table `count` is returned and logged as `{"event":"account_deleted","user_id":…,"erased":{…}}`;
- the table list is exported as `SUBJECT_TABLES` so a test can assert it against the schema.

**Tombstone (retained, stripped):**

```ts
data: { phone_number: '', email: null, full_name: null, date_of_birth: null, gender: null,
        auth_subject: `deleted-${randomUUID()}`, deleted_at: new Date() }
```

`phone_number` becomes `''` rather than `NULL` because the column is `NOT NULL` in the schema. The row
survives only as the `deleted_at`-stamped anchor that stops a re-signup from resurrecting the account.

**Deliberately retained: `AuditEvent`.** This is the one table that cannot be deleted without breaking a
legal requirement, so it is stated explicitly rather than quietly skipped:

- it is an append-only, hash-chained ledger (`hash = sha256(prev_hash + body)`, `seq` contiguous from 1,
  `prev_hash` UNIQUE). Deleting or rewriting any row makes `verifyAuditChain` fail for every later row and
  for the gap check (`apps/api/src/lib/audit-chain.ts`, E17-S4). Erasing a client must not be able to
  destroy the tamper-evidence of unrelated safety events;
- it holds no email, no name and no user id: `object` is `turn:<turn-uuid>` or `turn:<sessionId>:<n>`, and
  `detail` is safety-state/governance codes. After this transaction those ids no longer resolve to
  anything, so the retained row is an opaque event, not a link to a person;
- minimal retained shape is therefore *unchanged*: `(seq, actor, action, object, at, body, prev_hash,
  hash)` with the object being a dangling `turn:` reference. If the DPDP position later requires even
  that, the correct change is to truncate `object` to the action class and re-seal the chain from that
  point forward — not a row delete.

`apps/api/src/__tests__/account-delete.test.ts` (21 tests) asserts, for **each** table:

- a `deleteMany` was issued for it, and nothing outside the list was touched (`order.sort()` equality);
- the exact `where` — so a widened filter (a cross-subject delete) fails the test;
- `waitlistEntry` is *not* queried when the subject has no email/phone, i.e. no `IS NULL` sweep;
- ordering: `reminder` before `homework`, and `homework`/`turn`/`sessionSummary`/`governanceLog` before
  `sessionLog`;
- the tombstone update: `email === null`, `full_name === null`, `phone_number === ''`,
  `date_of_birth === null`, `gender === null`, `auth_subject` matches `/^deleted-/`, `deleted_at` is a
  `Date`, and the serialised `data` contains neither the email nor the original `auth_subject`.

Plus a schema-coverage block that reads `packages/prisma/schema.prisma` and fails if:

- any relation to `User` lacks `onDelete: Cascade` (18 found today);
- any model with a FK to `User` is missing from `SUBJECT_TABLES` — this is the regression guard for the
  E16-S7 class of bug: a new `user_id` column cannot be added without the erasure path being updated in the
  same commit;
- the test's own table list and the implementation's list disagree.
