# E15-S2 — A push to develop starts CodeBuild with no manual step; result shows as a commit status

Story: **"A commit pushed to develop starts a CodeBuild execution within 120 seconds with
nobody running `aws codebuild start-build`; the build result appears as a commit status on the
GitHub commit."**

**Status: partially_done — the trigger is installed, enabled and verified in AWS; the 120-second
end-to-end run is NOT proven here, because proving it needs a commit pushed to `develop`, and
this agent is not allowed to push to `develop`.**

`feat/E15-S2-webhook`, branched from `origin/develop` `ef715b0`.

## Step 1 — What changed (terraform)

`infrastructure/aws/evia-beta/pipeline.tf` — new resource after `aws_codebuild_project.main`:

```hcl
resource "aws_codebuild_webhook" "main" {
  count = var.codestar_connection_arn == "" || !var.enable_webhook ? 0 : 1

  project_name = aws_codebuild_project.main[0].name
  build_type   = "BUILD"

  filter_group {
    filter {
      type    = "EVENT"
      pattern = "PUSH"
    }

    filter {
      type    = "HEAD_REF"
      pattern = "^refs/heads/develop$"
    }
  }
}
```

- Anchored pattern `^refs/heads/develop$`: exactly one branch. Not `refs/heads/develop*`
  (would match `develop-x`), not `^refs/heads/*` (would deploy every branch).
- `build_type = "BUILD"` — a single build per push, not `BUILD_BATCH`.
- **No `pull_request_build` filter group**: PRs from `develop` do not build. Only the push does.
- The commit status is *not* produced by this resource — it comes from
  `report_build_status = true`, which is already on `aws_codebuild_project.main.source` and was
  left as-is (see Step 4, `reportBuildStatus: true`).

`infrastructure/aws/evia-beta/variables.tf` — `enable_webhook` (bool, default `true`) so the
trigger can be removed from code without deleting the project. Also documented in
`terraform.tfvars.example`.

## What is NOT proven / not done

1. **The 120-second end-to-end run is NOT proven.** No commit was pushed to `develop`
   (only the orchestrator may do that), so no build has actually been observed starting from a
   webhook delivery. The newest build in the project is still the manual one from before this
   change, which confirms nothing has fired since the webhook was created:

   ```
   $ aws codebuild batch-get-builds --ids evia-beta-build:a5ffe726-b5b5-4eb1-802a-f0d7f79963ab --region ap-south-1 \
       --query 'builds[0].{id:id,startTime:startTime,endTime:endTime,buildStatus:buildStatus,initiator:initiator,sourceVersion:sourceVersion}' --output json
   {
       "id": "evia-beta-build:a5ffe726-b5b5-4eb1-802a-f0d7f79963ab",
       "startTime": "2026-10-28T15:51:56.399000+00:00",
       "endTime": "2026-10-28T16:02:00.452000+00:00",
       "buildStatus": "SUCCEEDED",
       "initiator": "keel-deploy/botocore-session-1793202432",
       "sourceVersion": "develop"
   }
   ```

   `initiator` is an IAM session, i.e. somebody (the E15-S1 run) called `start-build` by hand —
   not a webhook. Everything above proves the trigger is installed, `ACTIVE`, filtered to
   `develop`, and that CodeBuild owns a live GitHub hook; it does not prove delivery latency or
   that the trigger actually fires. Any claim that "it works" is inference.
2. **The commit status on a real commit is NOT proven.** `report_build_status = true` is
   configured and the statuses are written through the same connection the source already uses
   (so the path is known-good from E15-S1's successful builds), but no status has been observed
   on a commit pushed after this webhook existed.
3. **The GitHub-side hook was not inspected directly.** No GitHub API token is available in
   this environment (`gh` is not installed), so the hook object could not be listed from
   `api.github.com`. Its existence is evidenced only by CodeBuild returning the hook URL
   `…/hooks/704417074` with `manualCreation: false`.
4. **`aws codebuild list-webhooks` does not exist** — the CLI rejects it
   (`An error occurred (ParamValidation): argument operation: Found invalid choice
   'list-webhooks'`). The CodeBuild API has no such operation; the webhook is only readable via
   `batch-get-projects` (`projects[0].webhook`) or `terraform state show`. That is what was used
   above.
5. **Pre-existing terraform drift left in place (not mine, not applied):** three
   `aws_ecs_task_definition` replacements + three `aws_ecs_service` in-place updates, caused by
   `image_tag` re-pinning (`41c5a5a9862b`) after a CodeBuild deploy, while state holds
   `53360b8b4cd8`. A full `terraform plan` will keep showing them until someone applies or
   refreshes. Applying it is a task restart across all three services, so it was left for the
   orchestrator.
6. The webhook was not exercised with a signed synthetic payload, because any accepted delivery
   for `refs/heads/develop` starts a real build + ECS rollout — a side effect outside this
   story's remit and one that would also fake the very test the orchestrator must run for real.

## How the orchestrator closes the acceptance criterion

1. Push any commit to `develop`.
2. Within 120 s: `aws codebuild list-builds-for-project --project-name evia-beta-build --region ap-south-1 --max-items 3`
   → newest build `startTime` must be within 120 s of the push, with no `start-build` call.
3. `aws codebuild batch-get-builds --ids <id> --region ap-south-1 --query 'builds[0].{sourceVersion:sourceVersion,initiator:initiator,reportArn:reportArn}'`
   → `initiator` should be the GitHub webhook (it contains the CodeBuild webhook URL / hook id),
   `sourceVersion` the pushed SHA.
4. The commit must show a CodeBuild status check (`STARTED` → `SUCCEEDED`/`FAILED`) on the
   commit page.
