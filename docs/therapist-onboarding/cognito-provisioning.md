# Therapist accounts: Cognito provisioning

The therapist portal has no sign-up. A therapist can sign in only if two things
are true:

1. **Cognito** holds a confirmed user in the therapist pool
   (`ap-south-1_eaJaK7g4g`, `evia-beta-therapists`) whose email is their
   username.
2. **Postgres** holds a `Therapist` row with the same email. That row is the
   allowlist the portal's `signIn` callback checks
   (`apps/therapist-portal/src/lib/auth.ts`) — a Cognito identity alone is
   never sufficient.

`scripts/provision-therapists.mjs` does both, idempotently, with passwords that
only ever exist in SSM Parameter Store and in memory.

## Seed accounts

| Therapist | Username | SSM parameter |
|---|---|---|
| Dr. Ananya Rao | `ananya.rao@okuvu.in` | `/evia-beta/therapists/ananya.rao/password` |
| Dr. Rohan Mehta | `rohan.mehta@okuvu.in` | `/evia-beta/therapists/rohan.mehta/password` |
| Dr. Priya Nair | `priya.nair@okuvu.in` | `/evia-beta/therapists/priya.nair/password` |

Each parameter is a `SecureString` holding a distinct 32-character password
generated by the script. To read one:

```bash
aws ssm get-parameter --name /evia-beta/therapists/ananya.rao/password \
  --with-decryption --query Parameter.Value --output text
```

To hand a therapist their password, read it and send it over a channel you
would use for any credential. Do not paste it into a ticket, a commit, a chat
log or the AWS console.

## Provision / rotate

```bash
export AWS_PROFILE=keel-deploy AWS_REGION=ap-south-1
export COGNITO_THERAPIST_POOL_ID=ap-south-1_eaJaK7g4g     # terraform output cognito_therapist_pool_id
export COGNITO_THERAPIST_CLIENT_ID=7bcn376flgj7rt35a05a14pk7g  # only for --verify

# first run: creates missing SSM parameters + Cognito users
node scripts/provision-therapists.mjs --verify

# `--verify` authenticates each password against the pool and reports the
# claims it got back. It never prints a token or a password.

# rotate every password (writes new passwords to SSM, then sets them)
node scripts/provision-therapists.mjs --rotate

# see what would happen, including which parameters are missing
node scripts/provision-therapists.mjs --dry-run
```

Safe to re-run: an existing `CONFIRMED` user is left alone, so a second
invocation does not invalidate a therapist's session. `--rotate` is the only
thing that changes a password.

Step 4 of the script (the `Therapist` row) runs only when `DATABASE_URL` is in
the environment. RDS is not publicly accessible, so run this from a host inside
the VPC (or supply `DATABASE_URL` from somewhere that can reach it):

```bash
export DATABASE_URL=$(aws secretsmanager get-secret-value \
  --secret-id evia-beta/database --query SecretString --output text | jq -r .database_url)
node scripts/provision-therapists.mjs
```

Without a `Therapist` row the sign-in succeeds at Cognito and is then rejected
by the portal with `?error=unauthorized` — that is the allowlist working, not a
bug.

## How the password reaches Cognito without leaking

`admin-set-user-password`, `put-parameter` and `initiate-auth` all take a
secret. The script writes the request body to a `0600` file in a private temp
directory and passes `--cli-input-json file://…`, deleting the file in a
`finally` block. Nothing sensitive appears in `argv` (readable via `ps`),
shell history, or script output. Passwords are printed nowhere: the script's
JSON report contains emails, parameter names, actions and token claims only.

## First-time prerequisites

- Terraform applied: the pool, the portal app client and its hosted domain
  must exist (`infrastructure/aws/evia-beta`).
- The operator needs `cognito-idp:Admin*User`, `ssm:GetParameter`,
  `ssm:PutParameter` on `/evia-beta/therapists/*`, and
  `secretsmanager:GetSecretValue` on
  `evia-beta/portal-cognito-client-secret`.
